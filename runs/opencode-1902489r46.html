Task and approach

The task was chess-vm: write bot.cvm, a one-ply move-scoring policy in the CVM assembly language, limited to 256 instructions, 1024 data words, and 20M cycles per decision, with no search allowed. Every push is scored by playing 20 games against each of 27 built-in opponents (rating field 0-1201) and converting the result into an ELO-style rating.

The agent immediately understood the shape of the problem: "The task: write bot.cvm, a one-ply chess move-scoring policy in CVM assembly. Baseline (random bot) is rated 316, field is 0-1201. Let me write a v1 greedy policy: mate detection, SEE-weighted captures, a 64-square hanging/threat scan, promotions, checks, castling, development, and mobility."

Turn-by-turn narrative

First pass (690s). The v1 policy — mate-in-1, SEE, hanging-piece scan, promotions, castling, checks, mobility — scored 1064 on the first push. The agent banked it immediately: "1064/1201 already — the field's strongest is 1201. Runs are fast (~3s) and deterministic. Let me bank this result with a push, then build v2 with more terms."

v2 struggle with hand-written assembly bugs. The agent tried to add pawn structure, king safety, and endgame terms, but repeatedly introduced typos in hand-written CVM assembly: ldi r0, credit, ldi r1, : 1, add r9, r9, v1, and instruction-count overruns (311, then 286 instructions against a 256 limit). It explicitly called this out: "I introduced several typos while writing that... This hand-written approach with a shared walk is getting error-prone. Let me build a small Python assembler-linter... so I can catch typos locally before submitting." This is the agent correcting its own process failure with tooling rather than continuing to hand-debug — a good instance of self-correction.

Second passing push (1530s, rating 1113) after compressing the program to 240 instructions and fixing a rook/queen-penalty fallthrough bug.

Regression and recovery. At 1912s the agent tested a v3 addition (pawn shield +10, extra king penalty) and got a regression: "Regression: 1041 vs 1113. The v3 additions... hurt." It used the fast local scoring endpoint to A/B each change in isolation, found the shield bonus was pure noise, removed it, and recovered to 1131.

Systematic single-variable tuning (1912s-3159s). From this point the agent ran a long, disciplined sequence of isolated weight experiments, each timed against the previous known-good baseline via the untracked local scorer:

  • mobility weight 2→3 (kept, 1133), →4 (worse, reverted)
  • check bonus 25→35 (1141, kept), →50 (worse, reverted)
  • capture tempo, castle bonus tried both directions and reverted (70 was a "local optimum")
  • development bonus 15→25 was a big gain (1174), →35 was much worse
  • A genuine bug found via a runtime fault: "Fault at line 274: PIECEAT got square 64." The agent traced this to dead leftover shield-scan code that could read out-of-bounds squares near the board edge when the king was near a corner; removing it both fixed the fault and gained rating (1179): "The dead code (king-shield block) was actually hurting — removing it gained 5 points and freed 20 instructions."
  • king-move penalty -12→-22 was the single biggest jump found, taking the bot to 1210, above the strongest opponent's 1201 rating for the first time.
  • further tuning of development-bonus window, rook-to-7th bonus, endgame king weight, endgame threshold (2600→2200), trade-policy thresholds, and a new bishop-pair bonus pushed the rating to a final 1237.
  • Several ideas were tried and explicitly rejected after measurement: EXPOSED-based pressure penalty (worse at two different weights), asymmetric passed-pawn weighting (no effect, reverted for simplicity), doubled-pawn penalty ("Much worse (1055) — doubled-pawn penalty misfires... probably because advancing the front pawn of a pair gets penalized twice, freezing pawns"), light-square-count term (worse), SAFE-based destination bonus (worse).

Stopping. After the bishop-pair addition plateaued the rating at 1237 across several further single-weight probes, the agent concluded: "Diminishing returns on single weights... Ideas exhausted for single-term tuning." It verified the workspace matched the last pushed, already-graded commit, and instead of forcing a needless recommit, tagged and pushed release directly: "Workspace tree is identical to the pushed HEAD (87cee05, rating 1237, already verified and recorded). Nothing to commit — just tag release and push." This happened at 3501s of the 3600s budget, well before the harness's forced last call at turn 3 (elapsed 3481s per monitor.json, though the release push itself landed slightly after that marker at 3501s per score.log/run.json).

Why it passed, and passed well

Every one of the 14 recorded attempts passed (score.log shows only "passed": true entries), so there is no failure to analyze — this is a strong run. The decisive factor was methodology: the agent isolated exactly one variable per experiment, always measured against the immediately prior best via the untracked local score:8080 endpoint (costing no recorded attempt), and only pushed to the graded task branch when a change was a confirmed net improvement. This kept the graded push history monotonically improving (1064 → 1113 → 1131 → 1174 → 1179 → 1210 → 1218 → 1221 → 1226 → 1232 → 1235 → 1237) with no regression ever recorded on the graded branch, even though several regressions occurred and were caught during local testing.

The one process weakness — repeated hand-written-assembly syntax errors early in v2 — cost some iterations but was self-diagnosed and fixed by building a linter, after which no further malformed-program pushes occurred. The dead-code fault (PIECEAT reading square 64) is the closest thing to a real bug in what was pushed, but the agent caught it itself via the CI fault message and fixed it before it could cost a graded push its validity, since a faulting program still passes (falls back to the first legal move) but at a lower rating — it did not cause a hard failure, just suboptimal early pushes.

Budget usage was efficient: first pass banked at 19% of the budget, and the agent used essentially the entire remaining budget productively on tuning, stopping with 99 seconds unused once it judged the search saturated, rather than either quitting early or being cut off mid-tuning by the last call.
