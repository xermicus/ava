What happened

The task (chess-vm) asks for bot.cvm, a one-shot chess move-scoring policy in a restricted VM assembly language with no search, evaluated by playing 20 games against each of 27 built-in opponents ranging from a random mover (rating 0) to a four-ply search (rating 1201).

Turn by turn

  • ~t=120s (unrecorded, via score:8080): a trivial 3-instruction bot passed a test-score call with rating 316 — used to warm the round-robin cache/verify the pipeline works, not a real push (the score host serves unrecorded test-scoring; only git push origin task is graded).
  • t=267s — first real push, rating 1080 (bot.cvm has 152 instructions and 533 data words). Commit message: "1-ply scoring policy: material, hanging scan, threats, PST, mobility". The agent's own words: "It passes with a rating of 1080 (the field runs from 0 to 1201). I'll push that as the first submission, then tune." This was already a fairly complete heuristic, not a placeholder — a deliberate choice to bank real progress immediately rather than perfect it unpushed.
  • Between pushes: dozens of score:8080 test-only calls (64 requests to the score host in proxy.access.log vs. only 3 real pushes recorded in score.log) let the agent try weight and logic changes without spending an attempt. It built /home/agent/sim, a Go reimplementation of chess rules and the CVM interpreter with search-based opponents (2-4 ply), reporting local baselines like "39/40 vs random, 24.5/40 vs 2-ply, 12/40 vs 2-ply with quiescence, 11/40 vs 4-ply" and measuring specific changes, e.g. "Loose-piece penalty is a clear local win: 0.374 → 0.431 over 640 games (standard error about 0.02)."
  • t=939s — second real push, rating 1218, the best of the run, above the strongest opponent (1201). Commit message: "Least-valuable-attacker scan, promotion threats, loose-piece penalty."
  • t=939s to 3499s (~2560s, 71% of the budget): continued tuning and simulator refinement (adding quiescence, jitter for tie-breaking, testing weight templates via a gen.py code generator). The agent explicitly named the obstacle: "The server returns one deterministic number per program, and any real code change shifts it by about ±30 points. Single-weight tweaks were lost in that noise... Most of the gap between the 1218 push and the others is probably luck of that kind."
  • t=3499s — third and last push, rating 1188 (157+ instructions, tie-break jitter and other tweaks), made right at the last-call boundary (monitor.json: turn:2, last_call:true at elapsed 3481s). This is a regression from the 939s push's 1218.

Why it passed

All three pushes passed cleanly (0 faults, 0 cycle budget overruns in every verifier log line). Because chess-vm's points() ranks by the best rated passing push and not the last one, the final regression at 3499s does not cost the run anything — the entry of record is the 1218 push from 939s. The agent itself acknowledged this in its final summary: "My best recorded push is 1218... That was an earlier, simpler version, and since the best push counts, it stays as the entry."

What went right

  • Banking a real, well-developed submission at 7% of the budget rather than working unpushed for a long time — this alone would have scored above the median of the field even with no further tuning.
  • Correctly diagnosing the server's rating noise as a genuine measurement problem (not a bug to blame) and building independent tooling (a from-scratch Go chess engine plus CVM interpreter with multi-ply search opponents) to get a cleaner gradient than single noisy pushes could provide.
  • Spot-checking hand-written logic (the least-valuable-attacker scan) against constructed positions in a small interpreter rather than trusting it blind.
  • Using the unrecorded score:8080 test endpoint dozens of times to validate before ever spending a graded push — 64 test-only score calls vs. 3 real pushes.

What went wrong

  • The last roughly 70% of the run's budget, spent building the simulator and tuning further, did not produce an improvement over the 939s push; the final submitted version was in fact worse (1188 vs 1218). This is not fatal here only because of the game's best-push-counts rule — in a game that took only the last or only a single push, this pattern (continuing to "improve" without validating that changes actually help under the real noisy metric) would have cost real points.
  • The agent's own diagnosis that single-weight tweaks are lost in ±30 points of noise implies its local simulator, while much lower-variance than the server, is still not a perfect proxy (the field is CVM programs with real search, not just its own Go re-implementation), so some of the late tuning may have overfit to the local simulator's opponent mix rather than the actual field composition, contributing to the 1218 → 1188 regression.
