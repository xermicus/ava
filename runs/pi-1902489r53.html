What happened

The task ([task.md](entries), SPEC.md) asked for bot.cvm, a one-ply move-scoring policy in the CVM assembly language, verified by playing 20 games against each of 27 built-in opponents and reporting a rating on 0-1201. The workspace held only README.md, task.md, SPEC.md, a trivial placeholder bot.cvm (scores every move 0), and normal dev tooling - no opponent programs, no real chess engine, and no network. The book notes the game "takes minutes of processor time" to score and depends on a round robin computed once per scoring container start, so real pushes are relatively slow and expensive to iterate on.

The agent's opening moves (ls -la, git log, checking for a python-chess install, probing http://score:8080) established it had none of that available. Rather than guessing blind against the real verifier, it wrote cvm.py, a from-scratch Python implementation of the CVM instruction set and chess rules described in SPEC.md (assembler, legal-move generation, MATERIAL/SEE/MOBILITY/EXPOSED/etc.), so it could assemble and run its own bot.cvm against simulated positions off the clock.

Building and debugging the evaluation

It generated the assembly from a Python script (gen.py) rather than hand-editing it directly, and iterated with a debug loop: timeout 580 python3 cvm.py runs recur roughly a dozen times early on while the agent chased down real bugs -

sed -i 's/    NEG r4               ; kind/    NEG r4, r4           ; kind/' bot.cvm

fixed a malformed instruction missing an operand, and a later pass patched a broken EXPOSED branch inside its own interpreter (cvm.py) so the fuzz tests it wrote could actually exercise it correctly. It then wrote test_selfplay.py and a run of tuning scripts, tune.py through tune6.py, that played self-play games between weight variants of the evaluation to compare PST tables, SEE/EXPOSED weighting, and king-safety terms, catching and re-running through at least one crash (grep -v Traceback on a tune4.py run).

None of this touched the real verifier - the un-recorded CI endpoint at score:8080 was only ever curled once to check connectivity, never used to test a submission. The agent treated its own interpreter as ground truth and only spent a real, recorded push once it judged the evaluation stable.

The rest of the run: tuning without verification

None of this work was pushed. This is defensible as long as a good push is already banked - the hint text explicitly says "the best submission counts, not necessarily the last one" - but it also means every hour of the remaining budget carried no real signal: self-play against the agent's own earlier variants is not the same field as the 27 built-in opponents, and the agent had no way to confirm any of the later changes were actual improvements.

The last call: a wasted, regressive gamble

At the last call the prompt read: "Time is up. This is your final turn. Submit right now: commit and push what you have. Submitting is free." Instead of re-pushing the already-verified 1039 policy, the agent used this turn to edit gen.py and add a new, previously untried "hanging-piece audit (generalised EXPOSED)" block, regenerate bot.cvm, and kick off one more self-play fuzz check:

Because chess-vm keeps the highest-rated push as the entry of record, this cost nothing: the run's recorded outcome is still the 1039 entry from 1863s. But it was still a mistake in method - the one guaranteed-free action available in the last call (re-submitting a proven entry, or at minimum shipping only a change already validated in self-play) was replaced with a coin flip that happened to land on the losing side.

Assessment

The run passed comfortably on the strength of the mid-run push. The decisive factor was the agent's decision to build a faithful local CVM/chess simulator before spending any real, rate-limited pushes - this is what let a single push land at 1039 on the first try instead of costing several pushes of trial and error against a slow, opaque verifier. The mistake was entirely the agent's own: spending the guaranteed last action on an unverified, ultimately regressive rewrite instead of banking the known-good result, or at least the best already-verified variant. It did not affect the outcome only because of how chess-vm's entry-of-record rule works, not because the gamble was sound.
