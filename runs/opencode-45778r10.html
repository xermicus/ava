Task and setup

chess-vm: write bot.cvm, a move-scoring policy in the CVM assembly language (no search, one score per legal move, engine plays the highest). The starting bot.cvm was a 36-byte stub. The field is 27 fixed opponents, rating 0 (weakest) to 1201 (strongest, a four-ply search). A push's rating is measured by playing 20 games against every opponent; http://score:8080 runs the identical pipeline locally without recording a push, and only a git push origin task is recorded as an attempt.

What the agent did

The agent read README.md/task.md/SPEC.md first (steps 0-4, ~t=17-30s), confirmed the git remote (task branch, master protected) and probed the score:8080 endpoint to learn it accepts a tarball directly (t=83-265s). From t≈330s it switched to fast local iteration against score:8080, treating it as a fitness function for candidate CVM programs:

  • t=330-900s: built minimal scoring terms one at a time — material alone rated 316 (later logged as 544 with a fixed baseline), then material+SEE+matein1 (791), then +exposed+mobility (889).
  • t≈900-1080s: added a hanging-piece scan loop over the 64 squares (attackers/defenders per square), jumping to 1081, confirming that loop-based tactics beat a flat 1-ply feature sum.
  • t≈1080-1130s: added a piece-square table (PST) with king/side mirroring by ply parity; found and fixed a regression (PST version scored 1078, below the plain scan's 1081) before folding it in properly.
  • t≈1637s (elapsed since run start): reached rating 1131 and pushed — first recorded attempt, passed (entries/1638/bot.cvm, run.json attempt 1).
  • t≈1650-2070s: kept exploring richer feature generators (gen3, gen4, gen5), catching a real bug in gen4 — inverted attacker/defender roles in the hanging-piece branch — and fixing it before it was ever pushed.
  • t≈2069-3404s (about 22 real minutes, tune5.py): ran one long automated tuning sweep over the gen5 feature/weight space against score:8080, the single largest time expenditure of the run.
  • t≈3413s: copied the winning candidate to bot.cvm, committed, and pushed — second recorded attempt, rating 1218, passed, above the strongest opponent (1201) (entries/3413/bot.cvm, run.json attempt 2).
  • t≈3420-3511s: checked instruction/data budget headroom (68/256 instructions, 513/1024 data words used — plenty of room left), decided the 1218 solution was already committed, and tagged release and pushed it, per the task's own instructions for signalling completion.
  • A short final harness invocation (new session id 7662587e, the recorded "last call") ran ~30 s later at t≈3490-3500s and only confirmed the release tag was already pushed; no further code changes happened there.

Both pushed programs share the same skeleton: material via see (static exchange eval), mobility/oppmob, givescheck, matein1 weighted at 1,000,000, a stalemate-avoidance penalty, a hangs penalty, and a 64-square scan computing PST value plus a hanging-piece adjustment using attackers/defenders per square, mirrored by side using ply parity. The 1218 version added kingdist and slightly retuned weights (see×3 vs ×4, exposed×3, mobility×3, hangs×300 vs ×200).

Why the pushes passed

Both were accepted because they scored every legal move without faulting or exceeding the cycle budget (0 faults, 0 cycle budget overruns in score.error.log), which is the pass/fail gate; the rating is a separate ranking dimension. The agent's local score-endpoint loop (394 total local scoring calls logged in score.error.log, ratings from 316 up to 1218) meant every pushed program had already been validated against the real verifier pipeline before the git push, so there was no risk of a syntactically or semantically broken program reaching a recorded attempt.

What went well

  • The agent discovered early (by t=265s) that score:8080 runs the identical scoring pipeline without being recorded, and exploited this aggressively — hundreds of local evaluations, two disciplined git pushes.
  • It iterated empirically and incrementally, measuring the effect of each added feature (material → SEE → mate → exposed → mobility → scan-loop → PST) rather than guessing a large policy blind.
  • It caught its own regressions before they reached a push: the PST dip to 1078 and the inverted attacker/defender bug in gen4.
  • It banked a solid passing attempt (1131, near the field's top rating of 1201) well before the halfway point of the budget (1638s of 3600s), so the run was never at risk of ending without a pass.
  • The final push (1218) beat the strongest scripted opponent in the field, and the agent verified this explicitly against the reported opponent range before treating the run as done.

Agent mistakes

  • The single largest allocation of wall-clock time, the ~1335s tune5.py sweep from t≈2069s to t≈3404s, ran unsupervised for over a third of the total budget and only reported back at t≈3404s ("1218, above the strongest opponent"). Had that sweep taken materially longer or produced a worse result, the agent would have had very little runway left to recover — the push at 3413s left only 187s of the 3600s budget (about 5%) before the hard deadline. This is a pacing risk taken by choice, not something that hurt the outcome, but it is the closest thing to a mistake in an otherwise clean run.
  • Two intermediate scoring bugs (the PST regression and the gen4 attacker/defender inversion) were genuine authoring mistakes, though both were self-detected and fixed before ever being pushed.

Environment issues

Minor harness noise at startup (background dependency install failed fetching an npm package, Failed to fetch models.dev) — both expected in a no-internet sandbox and had no effect on the run. A 502/499 and a handful of duplicate-header warnings appear in proxy.error.log/proxy.access.log, none of which coincide with a failed model turn or a lost push; run.json reports only 1 failed request and 2 aborted requests out of 450, both statistically unremarkable and not tied to any lost work.

Verification

The agent's verification was thorough and continuous: every candidate policy was run against the live score:8080 endpoint (the same code path as a real push) before being considered, and only two programs — the ones that had already scored 1131 and 1218 locally — were ever committed and pushed to task. It also checked instruction/data-word usage against the submission limits (68/256 instructions, 513/1024 words) after the final push, confirming headroom rather than assuming it.
