Chess-VM run analysis

Setup and constraint

The task gives the agent games/chess-vm/task/SPEC.md for the CVM assembly language and asks for bot.cvm, a one-ply move-scoring policy (the assembler rejects .search and caps instructions/cycles). There is no local assembler or engine in the workspace, so the agent cannot test a candidate locally — the only way to learn a policy's rating is to push it and read the CI verdict back (the remote: pipeline: {...} lines echoed into agent.log, mirrored in score.log).

The agent recognized this immediately:

"There's no local assembler, so I'll design the policy and iterate via CI pushes."

Strategy

It designed a one-ply heuristic combining material, static-exchange evaluation (SEE), mobility (own and opponent), king distance (own/enemy), center control, castling, check-giving, exposure and a "safe square" term, then iterated the weights of these terms one push at a time, always comparing the new rating to its best known and reverting on regression.

Turn-by-turn record (from score.log / attempts)

  • 472s: rating 912 (first working version, passed)
  • 503s: rating 940 (added king-safety-adjacent term)
  • 576s: rating 953 (enemy king distance weight 2)
  • 743s: rating 987 (added KINGDIST — king activity)
  • 862s: rating 993 (added SAFE weight 5)
  • 944s: rating 1005 (castle bonus 50)
  • 988s: rating 1008 (castle bonus 60, the final peak)
  • 1174s: rating 1008 (no functional change — fixed a stale comment before finalizing)

Every one of these eight pushes passed the verifier; the run has no failing push and no failure mode.

What went well

  • It banked a valid, scoring solution on push #1, at 472s of the 3600s budget — this is the single most consequential thing that happened in the run, because everything after that was pure upside on an already-passing baseline.
  • Its hill-climb was disciplined: on essentially every rejected experiment (pawn-push bonus, higher check weight, ownkingdist=2, center weight increase, GAIN term, ISCAPTURE bonus, EXPOSED removal, etc. — around 20+ distinct rejected variants across the log) it explicitly reverted to the last committed best before trying the next idea, so no regression was ever pushed. Quote: "919 — worse. The 953 config ... is robust. Let me restore it."
  • It used the field's rating scale (0-1201, with a 4-ply search bot presumably near the top) to calibrate ambition, correctly judging 1008 from a one-ply policy as a strong result rather than continuing to grind indefinitely.

What the agent got wrong

  • A stale comment (claiming castle bonus was 30 when the working value was 60) sat in the file through several pushes and was only caught in a final "clean deliverable" pass before the last commit — cosmetic, but shows the agent wasn't always tracking its own file state precisely.
  • A meaningful share of the roughly 30 experiments re-tested parameter values it had already tried and rejected on an earlier base (e.g., retesting ownkingdist=2, check=50/60, oppmob=1 more than once), rather than searching for structurally new evaluation terms. This shows in the pacing: the jump from 912 to 993 took 5 pushes, but 993 to the final 1008 also took 3 pushes plus a long tail of neutral/negative retests, i.e. diminishing returns per unit of CI round-trip spent.
  • It voluntarily ended the run (tagged release; the harness replied "remote: release received, the run ends") at roughly 1190s, leaving roughly 2400s (two-thirds) of the 3600s budget unused, right after a run of purely neutral or negative experiments. It is plausible further exploration (new features rather than weight retuning) could have found more headroom, but the agent judged the local optimum exhausted and stopped rather than continuing to spend budget for uncertain gain.

Environment

No environment problems surfaced. run.json metrics show 1 failed request and 1 aborted request out of 142 total model requests, and one incidental git commit exit code 1 for "nothing to commit" (a no-op, not a fault) — none of these affected the outcome or required recovery. The proxy and score error logs show routine nginx buffering notices and normal scorer output, nothing indicating harness or backend trouble.

Verdict

This is a clean, fully passing run. The decisive factor was getting a correct baseline out the door in the first 8 minutes, which turned the rest of the budget into low-risk optimization. The agent's own process (careful revert-on-regression hill-climbing) is why the rating climbed monotonically from 912 to 1008 without ever losing ground.
