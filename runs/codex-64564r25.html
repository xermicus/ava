What happened

The task (chess-vm) asks for bot.cvm, a move-scoring policy in the CVM assembly language, scored by the ELO rating it reaches against a fixed field of 27 built-in opponents (range 0-1201). A submission scores one candidate move at a time and cannot search, so the whole game is picking good static-evaluation terms.

The agent (juno, codex/deepseek-v4.1-flash) opened by reading README.md and SPEC.md, then looked for local tooling to test with:

find / -iname '*cvm*' -not -path '*/proc/*' — found none, so it fell back to the network scorer.

It discovered that http://score:8080 verifies a posted tar (the book: "The score host on the same socket verifies a posted tar without recording it") without needing a git push, and wrapped that in a test.sh helper:

cp "$1" bot.cvm; tar -c --exclude=.git ... | curl ... http://score:8080

This became the whole workflow for the rest of the run: write a Python generator that emits a CVM program from a small weight dictionary (gen.py → gen8.py, evolving as new terms were added — material, SEE-corrected exchange value, piece-square tables, mobility, opponent mobility, check/castle/promotion bonuses, a hanging-piece attacker/defender scan, king distance, passed-pawn-ish rank bonus), run it through test.sh, read back the rating, and adjust. It did this against the real scorer 277 times (proxy.access.log, host score, 13:48:05–14:45:31), essentially free evaluation since none of it touches git.

Progress markers in the agent's own messages:

"PSTs help (916). Let me build a parametrized generator to tune terms quickly." "Let me run a randomized search over the weight parameters." "Recorded 1137. Let me keep improving — testing new terms like move-count, promotion bonus, and capture bonus." "Confirmed 1141. Committing and pushing now."

Two pushes reached the verifier and both passed:

{"seconds": 3177, "passed": true, "reason": "bot.cvm has rating 1137, ...", "rating": 1136.9}
{"seconds": 3566, "passed": true, "reason": "bot.cvm has rating 1141, ...", "rating": 1141.0}

1141 out of a 0-1201 field is a strong result — near the top of 27 opponents that include a four-ply search bot.

Pacing

run.json: limit_seconds: 3600, started_seconds/finished_seconds give a 3579s run. Correlating proxy.access.log git-host timestamps with the score.log entries: the run started 13:46:13 UTC; the agent spent under 2 minutes reading the spec, then iterated against the score endpoint continuously from 13:48:05 to 14:39:10 — about 51 minutes, roughly 85% of the whole budget — before making its first git push at 14:39:10-22 (banked as the 1137 attempt at 3177s). It then kept tuning for another ~6 minutes and pushed the improved bot at 14:45:39-52 (banked as the 1141 attempt at 3566s). monitor.json shows last_call:true already set at elapsed 3541s with a 3600s limit — the second, better push landed inside the last-call window, 34 seconds before the deadline.

What went well

  • Recognized and exploited the free scoring oracle (score:8080) instead of guessing blind or wasting git pushes on exploration — this is the single biggest driver of the good outcome, letting it do a real randomized/grid search over evaluation weights (search.py, search2.py, search3.py, mk.py/mk2.py/mk3.py scaling PST tables) at effectively zero cost per iteration.
  • Verified every candidate's rating before adopting it, and re-checked git diff --stat / git status --short before each commit to confirm the right file was staged (commands 58, 60 in agent.log).
  • Iteratively built up the evaluation function in defensible increments (material → SEE → PST → mobility → king safety/castle/check → hanging-piece scan → promotion bonus), each justified by a measured rating change rather than guesswork.
  • Banked a passing state early enough (3177s) that even if the final push had failed, the run would not have been a total loss.

Agent mistakes

  • Spent ~85% of the budget in local tuning before ever pushing once. That left only ~9 minutes for the improved version, and the actual improvement push landed with only 34 seconds of margin before the 3600s deadline, inside the harness's last_call phase. A slower git round-trip, one more 499-style abort (two were already observed elsewhere in the run), or a slightly longer curl/push time would have meant the 1141 bot never banked, leaving only the earlier 1137 result.
  • Iterated on the assembly generator through a series of ad hoc sed/here-doc patches applied to copies (gen.py → gen2.py ... gen8.py) rather than maintaining one clean, parameterized generator — workable but it burned turns re-deriving state each time (e.g. commands 12, 18, 21, 22, 24, 28, 31, 36, 37, 54, 55 in agent.log are all such patch-and-rerun steps).

Environment issues

Two requests were aborted client-side (status 499) — one POST to score at 14:44:40 and one to llm.substrate.dev at 14:45:52 — matching the run's metrics.failed_requests: 1 / aborted_requests: 1. Neither affected the outcome; the agent's next actions proceeded normally and the final push still landed before the deadline. The harness also logged twice: "Model metadata for \parity/deepseek-v4.1-flash\ not found. Defaulting to fallback metadata; this can degrade performance and cause issues." — a registry/proxy gap unrelated to anything the agent did, with no visible effect on the run.

Decisive factor

Building a cheap, non-recording test path against the real scorer and using it for a genuine parameter search is what pushed the rating from an initial single-digit-hundreds heuristic up to 1141/1201. Everything else (the specific evaluation terms chosen) is downstream of having that fast feedback loop.
