chess-vm run analysis

Task and setup

The agent had to write bot.cvm, a one-ply move-scoring policy in the CVM assembly language (SPEC.md), verified by playing 20 games against each of 27 built-in opponents (ratings 0-1201) and converting the score to a rating. points() never executes the program, so the entry of record is the best-rated push, not the last (per task.md: "The best submission (recorded on task branch pushes) counts, not necessarily the last one."). The task also exposes a local, unrecorded scoring path: tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080, letting the agent dry-run candidates for free.

What the agent did

  1. Orientation. Read README.md, task.md, SPEC.md, and the starter bot.cvm (a 3-instruction stub that scores every move equally, rating 316 per the field). Confirmed the score socket worked (time (tar -c --exclude=.git . | curl ... http://score:8080)).
  1. Baseline (push 1, seconds 221, rating 1105.3). Wrote v1.s: mate-in-1 detection, stalemate handling, material, weighted opponent-mobility, mobility, give-check and castle bonuses. Verified via the score socket first ("First version rates 1105 ... Committing and pushing it as the baseline"), then committed and pushed. score.error.log confirms bot.cvm has rating 1105, 0 faults, 0 cycle budget overruns / ... passed at 13:02:34, matching the recorded attempt at 221s.
  1. Tuning infrastructure. Built gen.py (a $VAR-templated code generator for the .s source) and run.sh/search.py (tar the generated bot.cvm, POST to http://score:8080, parse the rating out of the JSON verdict). Ran parallel sweeps of weight combinations: for o in 0 1 3 5 8; do for m in 0 2 4; do ... & done; wait; done. Noted upfront that "results are noisy (±30)."
  1. Structural upgrade (push 2, seconds 1380, rating 1240.3 — the eventual best). Added a shared threat-estimation term (SEE-like: what the opponent could win from an attacked piece, and the mirror bonus for enemy pieces threatened) in v3.s. Ran a long-lived search.py sweep in the background (sleep 120, then sleep 600, polling its output file) and picked up a result above the strongest opponent: "Search found 1240 (above the strongest opponent at 1201). Pushing that while the search keeps running." The push (v3.s with tuned params) landed at 13:22:09 in proxy.access.log (git-receive-pack, 94s upload) and matches the recorded attempt at 1380s / rating 1240.3.
  1. Noise-aware evaluation. Recognizing that single dry-runs were too noisy to compare structural variants reliably ("The noise is too large to judge structural changes from single runs"), the agent wrote meanev.py to average ratings over several small weight perturbations per variant (v3.s vs v4.s, 16 perturbations each) instead of trusting one number.
  1. Further structural work (v4, v5, v6). Added a king-attack term with an eking branch, then endgame mop-up/repetition terms in v5.s. While extending to v6.s the agent introduced and caught a register bug ("Correction needed first: the king-zone block reuses r1, which still holds the enemy king square for the mop-up term. Switching it to r13, then running the toggles"), but the fix script's chained str.replace calls (e.g. replacing r1,, r1\n, r1, r1, patterns with r13-based text) produced the invalid register r133. score.error.log shows the fallout: 48 consecutive, identical failures in a 4-second window (13:50:12-13:50:16): bot.cvm line 237: 'r133' is not a register, the registers are r0 through r15 / ... failed, from the background parallel sweep hammering the broken file before the agent moved on. The v6 branch was not repaired; the agent fell back to v5's known-good structure.
  1. Final push (push 3, seconds 3494, rating 1210.4). Generated bot.cvm from v5.s with a specific parameter set and pushed ("Add LVA scan, mop-up and repetition terms"). This landed inside the run's last_call window (monitor.json: elapsed_seconds:3481, last_call:true) at 13:57:19 in proxy.access.log. It scored lower than push 2, which the agent explicitly flagged in its final report: "The final push scored 1210, which is lower, but the best push is the one that counts," backed by its own noise analysis (v5 averaged ~1213 over 12 perturbations vs. ~1200 for the push-2 settings over 16, i.e., v5 is "structurally better even though its single push scored lower").
  1. Final report. The agent explained its evaluation function in the final message, flagged the evaluation noise (±20-50 rating points between near-identical settings) as a real caveat on the 1240 figure, noted an untested version (fork detection, king-zone safety, pawn-push bonus) whose search run was cut off, and explicitly declined to tag release since it judged there was more to gain.

Why it passed

All three pushes passed verification outright — the verifier never had to reject a submission the agent believed was ready, because every candidate had already been dry-run through the unrecorded score:8080 endpoint. Since chess-vm ranks by the best-ever push and not the last, the mid-run 1240 push is the entry of record: run.json's attempts list and score.log both show three passed:true verdicts (1105.3 / 1240.3 / 1210.4), and entries/1380/bot.cvm holds the winning source.

Mistakes and their cost

The r133 register bug (self-inflicted by an unchecked chained text substitution) cost real wall-clock time — 48 identical failed dry-runs inside a 4-second window is evidence of a sweep script retrying a structurally broken file rather than the agent catching the error after the first failure — but it never reached a real push and did not affect the recorded outcome. Not tagging release is a minor process nit the task explicitly makes optional.

Environment notes

score.error.log shows the scoring container's prepare() step running twice within the first two minutes with an interleaved, timestamp-less received SIGTERM, shutting down line, consistent with a duplicate scorer process where one instance was killed and the other kept serving; this had no visible effect since scoring continued normally for the rest of the run. Separately, score.error.log's last line is timestamped 13:50:16, roughly 7 minutes before the run actually ended (13:57:30) and 7 minutes before the third, real, recorded push at 3494s (13:57:19) — that push is fully accounted for in run.json, score.log and entries/3494/bot.cvm, so this is a log-collection gap in the sidecar's stderr capture rather than a scoring or harness failure.
