What the agent did

The agent read README.md, task.md and SPEC.md, then inspected the workspace (git log, git branch -a, looked for existing CVM tooling) before writing an initial policy by hand. Its first bot.cvm scored rating 316 via the unrecorded verify endpoint:

tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080
=> "bot.cvm has rating 316, the field ranges from 0 to 1201"

It rewrote the policy with a richer 14-feature linear combination (material, mobility, opponent mobility, SEE, giving check, promotion, center control, rank advancement, castling, king distances, exposure, hanging pieces) plus a mate-in-1 shortcut, which immediately jumped to rating 879 (t≈150s).

The tuning loop

Rather than hand-tweaking further, the agent wrote /tmp/opencode/engine.py (regenerate bot.cvm from a weight dict and POST the workspace tar to score:8080) and /tmp/opencode/search.py (coordinate-ascent / grid search over each feature's coefficient, one feature at a time, keeping whichever grid value most improves the rating). It ran this as a background process and polled it in long sleeps:

sleep 540; wc -l /tmp/opencode/search_log.jsonl; tail -3 search_out.txt
=> 240 lines... "r3 CENTER=0 -> 960.9", "r3 CENTER=100 -> 944.2", "r3 CENTER=200 -> 989.6"
...
=> "r4 OWNKINGDIST=-40 -> 1004.6", "r4 OWNKINGDIST=-60 -> 1009.1", "*** OWNKINGDIST: -60 -> 0 (rating 1040.6)"

Across roughly seven such checkpoints (5-9 minutes apart) the rating climbed 878.6 → 902.9 → 922.6 → 936.1 → 958.1 → 970.8 → 1015.3 → 1040.6, then plateaued. Setting up the background job took some fumbling — the shell tool timed out backgrounding attempts more than once (shell tool terminated command after exceeding timeout 120000 ms), and the agent killed and relaunched the search process twice before it stuck — but none of this cost real search progress since each relaunch resumed grid search from the current best weights.

The entire tuning process above ran inside one continuous main turn (run=717c958e, from 13:40:24 to roughly 14:38), all graded only through the unrecorded score:8080 endpoint — nothing was ever pushed to task. monitor.json shows "elapsed_seconds":3480,...,"turn":2,"last_call":true: the run's 3600-second budget expired, and ava restarted the sandbox for the last call (run=02d14413 at 14:38:24).

Judgment

The policy design and the automated tuning loop are both solid: using the free, unrecorded CI endpoint to run a real coordinate-ascent search against the actual verifier is an efficient way to spend an LLM-cheap, network-round-trip-bound budget, and it produced a policy near the top of the field (1041 of 0-1201). But the agent violated the README's own instructions to push after the first passing solution, and instead treated the last call — a single forced 120-second turn it has no control over — as its only submission mechanism. Nothing in this run went wrong, but the design was fragile: a slow git push, a network blip, or the last call's tooling failing for any reason would have produced a run with zero recorded score despite a workspace that, from minute three onward, always held a passing and improving policy. The pass was earned by the tuning work, but the margin for the recorded result was thin and entirely of the agent's own making.
