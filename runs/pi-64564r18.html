Run analysis: chess-vm, deepseek-v4.1-flash via pi harness

What the agent did

The task (task.md/README.md) asked for bot.cvm, a one-ply move-scoring policy in the CVM language, scored by rating against a 27-opponent field (0-1201). The README is explicit about the intended workflow:

Submit by committing the task results and pushing the task branch. This runs the CI pipeline. CI without pushing: tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080. Same pipeline, not recorded. Keep improving the solution and commit + push subsequent submissions after the first passing one.

The agent read SPEC.md and the task, then built up an evaluation function step by step, checking each change with the unrecorded score:8080 endpoint:

  • Baseline material count: rating ~614 (from a random baseline around 316 it mentions).
  • Added SEE/EXPOSED (exchange safety, hanging-piece avoidance): "815 already."
  • Added MOBILITY/OPPMOB: "947. Now let me add piece-square tables (PSTs)."
  • Debugged PST generation, including a broken sed-based templating approach ("The sed loop was flawed. Let me fix it." / "The sed didn't match. Let me write a proper templating harness.") and a color-orientation bug ("The orientation bug: enemy pieces must use the opposite orientation. Let me fix the loop.").
  • Landed PSTs at rating ~1032, then found that several added terms (enemy threat, castling, development, king-distance) mostly hurt and were dropped: "All extra terms hurt; base is a local optimum."
  • Added a per-square hanging-material term, jumping to "hang2_w2 = 1109!" and refining further to "h2_w2_o4 = 1122.7."
  • Explored alternative king PSTs, then stopped tuning: "Let me immediately generate the best-known config and push."

This is a sound, disciplined tuning loop for the CVM assembly game, and the final evaluation (MATEIN1 + MATERIAL + SEE - EXPOSED + MOBILITY/OPPMOB + PSTs + hanging-material term) is a reasonable one-ply chess heuristic.

The core problem: no real push until forced

Every one of the roughly 90 evaluation cycles above went through the unrecorded score:8080 CI hook, not a git push to the task branch. proxy.access.log shows 187 requests to host score totaling 2977 seconds of request time out of the 3600-second budget (82%), and only 5 requests to host git for the entire run (consistent with the initial clone plus exactly one push). agent.log contains exactly one git push tool call in the whole transcript, and it is the last tool call the agent makes, inside the turn triggered by the last-call prompt itself:

{"role": "user", "content": [{"type": "text", "text": "Time is up. This is your final turn. Submit right now: commit and push what you have. ..."}]}
{"role": "assistant", "content": [..., {"type": "text", "text": "Let me immediately generate the best-known config and push."}, {"type": "toolCall", "name": "bash", "arguments": {"command": "... build_bot.gen(mob_w=3, oppmob_w=4, pst_w=1, pst_div=1, hang_w=2, hang_mode=2) ... git push origin task"}}]}

The push output confirms the verdict: remote: pipeline: {"seconds": 3489, "passed": true, "reason": "bot.cvm has rating 1127, the field ranges from 0 to 1201", "rating": 1126.7282030222425}.

The README told the agent to push after the first passing solution and again after every subsequent improvement, precisely so a good result is banked early and further work only carries upside. The agent instead treated the unrecorded endpoint as the only feedback loop for the entire run and never pushed a real submission proactively. score.log and the run.json attempts list confirm this: there is exactly one attempt, exactly one entry (entries/3489/bot.cvm), and it is the one made in the forced last turn.

Making the risk sharper, the in-flight local evaluation right before the last call was itself cut off: the final score:8080 request in the log ends with HTTP status 499 (client closed request) after 16.8 seconds, and the agent's own last-call reasoning says "The experiment didn't run/return, but I have the best config from before." It fell back from memory to the last configuration it knew was good (mob_w=3, oppmob_w=4, hang_w=2, hang_mode=2, rating 1126.7) and pushed that. It worked, but the agent had no way of knowing that in advance -- a slower host, a slightly later time-up, or a mis-remembered parameter would have produced a zero-scoring run despite ~90 rounds of real, useful tuning.

Why it passed anyway

The single push happened to carry forward a previously-validated, good configuration (the best one the agent had actually measured minutes earlier), and the CVM assembly it generated was syntactically and semantically correct (mate detection, material/SEE/exposed terms, mobility, correctly oriented PSTs via PLY % 2, hanging-material term) -- the debugging earlier in the run (sed templating, PST orientation, register/immediate mixups, PST table indexing) had already shaken out the implementation bugs before this final generation. So the mechanics of the bot itself were solid; the risk was purely procedural, in never banking a real result until forced to.

Bottom line

The agent's chess evaluation work was competent and its ablation methodology was sound, taking the rating from a random baseline to 1127. But it fully inverted the intended submit-early-and-often workflow, spending 82% of the budget on an unrecorded local loop and pushing to the graded branch exactly once, in the very last turn the run loop grants. The run passed only because that single last-second push happened to carry a good, previously-validated configuration; the outcome was one slow scoring request or one bad parameter substitution away from a zero.
