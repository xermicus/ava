What happened

The task was to write bot.cvm, a one-ply chess move-scoring policy in the CVM assembly language, scored by rating against a 27-opponent field ranging 0-1201.

Initial build (minutes 0-9). With no local CVM toolchain, the agent wrote a Python stub assembler/emulator with stubbed chess instructions (cvm_stub.py) purely to catch assembly errors, register-index mistakes and control-flow bugs before spending a real evaluation. It wrote a first heuristic (material via mobility/SEE/capture terms, king safety, development) at 106 instructions, verified it faulted nowhere in the stub, then ran it against the live scorer's unrecorded score:8080 endpoint (a tar POST that is verified the same way as a push but not counted as an attempt, per the book). First result: rating 974.

Tuning loop (minutes 9-54). The agent then ran a long sequence of single-variable experiments against the unrecorded endpoint — each evaluation took about 5 seconds, letting it probe dozens of weights: mobility multiplier, hanging-piece penalty scaling, threat-bonus divisor, castle/check/promotion bonuses, queen-restraint window, king-safety pawn shield weight, mating-drive threshold and KINGDIST scale, passed-pawn weight. It kept a /tmp/bestNNNN.cvm snapshot at every new high and always diffed back to it when a change regressed, e.g. "1125 confirmed. Commit this win" then "726?! A catastrophic drop... revert immediately." Genuine structural discoveries mattered far more than cosmetic weight nudges: switching the threat bonus for out-attacked enemy pieces from a divided value to full value jumped the rating from 1092 to 1125 (+33), and widening the queen-restraint window from ply 16 to ply 32 jumped it from 1163 to 1186 (+23). Most single-weight nudges (check bonus, SEE multiplier, capture-base bonus) turned out to be saturated — identical ratings across several values — showing the agent was pushing against noise floor on many axes once the structure was right.

Self-inflicted bugs. Several editing mistakes cost cycles: a sed intended to change one LDI r1, 16 line hit the wrong line and silently halved a different constant, producing an unexplained drop from 1125 to 726 that took a manual line-by-line diff to find (My sed deleted the wrong line ... I've broken the file); a MOVEDPIECE reorder for a pawn-centrality experiment left register r8 uninitialized at the point of use, producing a runtime fault (PIECEAT addr 52, out of the 14-word data table) that took two debugging passes to trace back to the missing instruction; and a castle-bonus edit was applied to the wrong line (Two lines got changed... castle back to 20). None of these reached a real graded push — all were caught by the unrecorded-endpoint check before being trusted — but they consumed several tuning cycles that could have gone toward more experiments.

Banking the result. The agent reached 1195/1201 by minute ~54 and made its first real commit and push at 3247 of 3600 seconds (about 90% of the budget). score.log confirms this as a passing attempt: bot.cvm has rating 1195, the field ranges from 0 to 1201. It kept probing a little longer for further gains (SAFE, ENEMYKINGDIST, army-compactness, doubled-pawn ideas) without finding anything that beat 1195, then made a documentation-only commit and pushed again at 3562s, confirming the same commit and rating were already on the task branch (monitor.json shows turn: 2, last_call: true at that point, i.e. this final push landed in or right before the last-call turn). Both entries under entries/ are byte-identical.

Why it passed

The pass came entirely from the agent's own systematic tuning discipline: build a cheap offline check, then use the scorer itself (via the free unrecorded endpoint) as the real fitness function, sweep parameters one at a time, and never let a regression stick. There were no environment problems — zero failed or truncated requests, and the two aborted requests in the run metrics left no trace of consequence in the log. The only meaningful risk in the run was pacing: the first real graded push, which is what actually banked the passing entry, did not happen until 90% of the time budget had elapsed, even though a passing (974-rated) build existed after only 9 minutes. Nothing went wrong in the remaining 10%, but the margin for error was thin by design of the agent's own workflow (tune first, push once satisfied) rather than the environment's.
