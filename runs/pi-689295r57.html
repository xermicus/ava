Run analysis: chess-vm, deepseek-v4-flash on pi

Task and setup

The agent had to write bot.cvm, a chess move-scoring policy in the CVM assembly language, verified by playing 20 games against each of 27 built-in opponents and reporting an Elo-style rating. No local CVM interpreter/tooling was available in the sandbox (confirmed explicitly: "No local CVM tooling, so I'll rely on CI for verification."), so all feedback had to come from the verifier itself, either via a real push to the task branch (recorded, kept as an entry) or via tar | curl http://score:8080 (graded the same way, not recorded). The run was given 3600 seconds.

What the agent did, iteration by iteration

After reading the README and SPEC.md, the agent wrote an initial policy combining material, static-exchange-evaluation (SEE) safety, mobility, and king distance, and pushed it. From there it iterated by hypothesis and measurement:

  • v1 (213s): material + SEE + mobility + king distance -> rating 884
  • v2 (274s): tuning -> 896
  • v3 (314s): rook-on-7th-rank and bishop-diagonal bonuses -> 906
  • v6 (382s): rook7th 40 / bishop-diag 35 retune -> 911 (v4/v5 were score-endpoint-only trials that did not beat the running best and were not pushed)
  • v7 (453s): added piece-square tables (PST) -> 939
  • v8 (498s): PST scale 0.5 -> 962
  • v9 (554s): check bonus 50 -> 977

Every one of these 7 recorded pushes passed and improved on the last (score.log shows 7/7 passed, monotonically increasing rating). Between pushes the agent ran many more trials through the score endpoint (44 requests to score:8080 against 18 to git, i.e. roughly 6 silent trials per recorded push) and only pushed once a change beat the current best, for example rejecting a queen-early-movement penalty ("Queen-early penalty (959) worse than 977. Revert.") and a larger check bonus of 55 ("Check 55 (975) slightly worse than 50 (977)").

Ending the run

After v9 landed at 977 (554s), the agent spent further turns probing nearby variations of the same ideas: combining check bonus with capture, removing the rook-7th/bishop-diagonal bonuses to isolate their contribution (974 without them, confirming they were worth keeping), and re-confirming the check-bonus optimum. None beat 977. It concluded: "I've extensively tuned. v9 at 977 is my strong local optimum. Let me restore v9, commit/push, and tag release." It then did a final structural sanity pass (256 data words under the 1024 limit, ~85 instructions under 256, cycle budget under the 20M limit) before tagging and pushing release at 996 seconds -- only 27% of the 3600-second budget.

Why it passed, and what was left on the table

The run is a clean pass: a first working entry was banked early (213s) and every subsequent push improved on it, so there is no unbanked-work risk and no environment failure (one aborted LLM request and no failed tool calls, immaterial to the outcome). The decisive factor was the agent's discipline of testing changes against the unrecorded score endpoint before ever touching the task branch, which is why 7/7 recorded pushes passed and rose monotonically.

The main critique is pacing: the exploration that led to 977 was narrow -- a handful of hand-picked positional bonuses (rook on 7th, bishop diagonal, PSTs, check bonus) tuned mostly by nudging magnitudes up or down, not a systematic sweep of the evaluation space the CVM instruction set exposes (e.g. pawn-structure terms, more granular king-safety weighting, tempo, hanging-piece detection beyond a single SEE call). Having found several small wins in quick succession, the agent declared a "local optimum" from a handful of variations and stopped, leaving about 2600 seconds -- more than four times what it had already spent -- unused. Since chess-vm rewards further rating gains rather than a binary pass, and the task explicitly says the best submission, not the last, counts, spending more of the budget on materially different ideas (rather than variations on the same few bonuses) was the available upside the agent did not take.
