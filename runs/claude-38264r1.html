chess-vm run analysis

Setup

The task, chess-vm, asks for bot.cvm, a move-scoring policy written in the CVM assembly language, which cannot search (no .search, 256 instructions, 1024 data words, 20M cycles) and is scored by rating against a fixed field of 27 opponents (including up to a 4-ply searcher). Budget: 5400s. The agent (jacob, Claude Opus 5.5, effort max) ran a single long session that reached two turns before the last call at elapsed 5340s, and made five passing pushes.

What the agent did

  1. Orientation (first few tool calls): read README.md, SPEC.md, the starting bot.cvm, checked git state, then immediately pushed the unmodified starting bot to the live scorer to get a baseline — random-ish bot rated 316 (field 0-1201). It also probed the score server and checked what local tooling (Python, chess libs, compilers) was available in the sandbox.
  1. Infrastructure build (roughly the first third of the run): rather than tune blind against the slow live verifier, the agent wrote from scratch, in C, a full chess move generator (chess.h), a CVM assembler/interpreter (cvm.h), and a tournament driver (main.c) that could replay the opponents' own CVM programs. It validated the move generator with a perft test before trusting anything built on top of it ("Perft is fully correct"). It then wrote two hand-crafted calibration bots (v0a, v0b), scored them locally and on the real CI, and used the comparison to sanity-check the simulator.
  1. First bug and first push: a Python evaluation-program generator (gen1.py) produced programs that faulted; the agent built an instruction tracer (trace.c) to find the cause — a variable-shadowing bug in its own hand-rolled assembler's immediate/label resolver — fixed it, saw local win rate jump from 14% to 50%, confirmed on the real CI (v1 rated 977 vs. the 813 estimate), and pushed it at 761s, its first passing (and immediately good) entry.
  1. Endgame diagnosis (761s-2494s): rather than guess at further improvements, the agent instrumented its simulator to dump full game records and specific FEN positions, then used scripts (findgames.sh) to pull out drawn/lost games by outcome reason. It found the bot was repeating positions and drawing when materially ahead, and had weak technique in basic endgames (KQK mated in only 6/16 local test games, KRK 4/16, KBBK 0/16). It iterated the evaluation function (gen2.py, king-distance and mobility terms) and pushed twice more, at 1579s (1005) and 2494s (1165), tracking real gains through the same discover-a-losing-pattern -> add/tune a term -> re-measure loop.
  1. Ablation harness and long tuning stretch (2494s-5005s, nearly half the budget): the agent built a parallel CI-scoring helper (ci.sh, cilib.py) after discovering the live scorer tolerates ~4 concurrent requests in ~12s, and a switchable/#IF-gated evaluation source (gen3.py onward) so it could run parameter sweeps and feature ablations without hand-editing CVM by hand each time. It used per-move score dumps against specific FENs to debug why one change (an enemy-king-distance term) made KQK endgames worse rather than better, and iterated through v4-v6 with sweeps over noise, check bonuses, mobility thresholds and win-threshold parameters, backed by 8-16-seed local tournaments to reduce noise in the comparisons. No push happened in this stretch until 5005s (rating 1258), the largest of the five gains and the run's peak.
  1. Endgame: while a background parameter sweep (b10.py) was still running, the agent noted a v7 idea (king-safety plus "check and threat" terms) had a bug that read outside its data area in local testing, and explicitly dropped it rather than debug it further under time pressure. It killed the background sweep (pkill, with a self-inflicted near-miss where the first pkill -f b10.py matched its own invoking shell and had to be redone with a tighter pattern), picked the best-average local configuration (EKDW=3, mean ~1164 over 16 seeds), and pushed at 5441s, during the last-call phase (monitor.json shows turn 2, last_call: true at elapsed 5340s). That push scored 1252 on CI — lower than the 5005s push's 1258 — which the agent attributed correctly to CI-rating noise (it explicitly reasoned the two versions were statistically close, ±40 swings observed) rather than a real regression, and it said so plainly in its final summary instead of overclaiming improvement.

Why the pushes passed

Every one of the five pushes produced a program that scored a decision for every move (no fault, no cycle-budget exhaustion), so verification never failed on execution grounds — see score.log, five passed: true verdicts. Points/standing use the highest-rated passing entry, so the 1258 push (branch commit 37af098, per the agent's own summary) stands as the run's peak, comfortably above the strongest opponent's rating of 1201.

Assessment

This is a strong, methodical run: the agent replaced a slow, noisy oracle (live CI, seconds per game, tens of seconds per full rating) with a fast, validated local proxy (perft-checked move generation, faithfully reimplemented CVM semantics, replica opponents) early, and used it to find and fix real weaknesses (an assembler bug, repetition draws when ahead, poor basic endgame technique, hanging pieces) through direct inspection of played games rather than guesswork. It banked a passing, good entry (977, already close to the eventual median of the field) at just 14% of the budget, and kept improving and re-confirming on the real scorer throughout, never trusting the local proxy over the live one when they disagreed (the v2 regression). The one soft spot is pacing: after the 2494s push there was a roughly 2500-second stretch — nearly half the total budget — without an intermediate push, all of it spent on parameter sweeps and endgame debugging; had the run ended a few minutes earlier than it did, the agent would still have banked its 5005s push (1258), so this was not fatal, but it was a stretch of the run with no fresh safety net. The final push, made under last-call time pressure from a local-only average rather than a fresh CI number, came in slightly below the run's peak, but the agent understood and stated this correctly rather than being misled by it.
