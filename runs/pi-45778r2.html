Analysis: r2wars-x86-32 run

Outcome

The run passed on its only recorded push, at second 3538 of the 3600-second budget, inside the last call. score.log holds one line, {"seconds": 3538, "passed": true}, run.json records a single attempt at 3538, and the only entry is entries/3538/warrior.x86-32.asm. The proxy access log shows exactly one git-receive-pack (the final push, which created the task branch) and two unrecorded score POSTs (the tar probes).

What the agent set out to do

The task asks for warrior.x86-32.asm assembling to 1-512 bytes; any assembling warrior passes, and the fights decide value. Within the first minute the agent read this correctly. After a tar probe with a one-byte nop warrior returned {"verdict": {"passed": true}}, it wrote (assistant message at ~52s): "CI only checks acceptance. The real score likely comes from a hidden tournament." Its plan was therefore to understand the r2wars ESIL engine deeply and build a strong "arena sweeper" warrior, then submit the best one.

Turn-by-turn

There were two harness turns: one long main turn from the start until the time limit, and the last call. The pi log's 84 turn_start events are model turns inside that session.

  • 0-52s. Explored the workspace, read the README and task, listed the r2wars examples, ran one fight, inspected git. At ~45s it posted a tar of the workspace to score:8080 and got {"passed": false, "reason": "no warrior.x86-32.asm in the submission"}. At ~49s it wrote nop to warrior.x86-32.asm, assembled it (90 bytes) and posted again, getting {"passed": true}. It had thus already discovered the trivial pass condition.
  • 52-162s. Reverse-engineering detour. It tried to decompile /opt/r2wars/bin/r2wars.dll with radare2's CIL plugin, read the PDB, and disassembled engine methods, but the CIL output was unreliable. At ~162s it concluded: "The CIL plugin is unreliable. Let me pivot to empirical testing."
  • 162-1116s. Empirical engine probing. It built testop.sh, cyc.sh and stats.sh harnesses, tested which opcodes trap, whether memory is shared, how rep stosd advances, and SSE stores. Two single tool calls dominated this stretch: one from ~184s to ~515s (the multi-opcode trap test) and one from ~557s to ~872s, each blocking for five-plus minutes.
  • 1116-1751s. Built the candidates. sweep2 (a self-locating stosd dword-fill of the whole arena except its own code, with a byte tail) appeared at ~1116s, then spray, spray2, and a rep stosd variant. It tested sweep2 against the examples: it beat jordi but lost to pancake (winner: pancake.x86-32, 1-2).
  • 1751-2801s. Cycle-cost experiments and a final attempt at an "oracle" warrior that would scan for a non-zero cell and write there, which it never finished because rasm2's x86.nz assembler mishandled a far conditional jump to the label notfound. It fixed the label at ~2801s.
  • 2801-3484s. A long gap with little visible progress; the 10-run stats.sh at ~2372s reported wins=0 ... draws=10 for every pairing, a parsing bug that told the agent nothing. A later simple loop at ~2498s showed sweep2 beating spray2 4 of 5.
  • 3484s. The last-call prompt arrived: "Time is up. This is your final turn. Submit right now...".
  • 3484-3538s. The final call. Its first command, cp /tmp/wt/sweep2.x86-32.asm warrior.x86-32.asm, failed: /tmp had been wiped between turns. It then recreated sweep2 from memory, re-assembled it, confirmed the hex matched the previously verified bytes e8000000005bfcb8f4f4f4f4..., committed and pushed. The push output was remote: pipeline: {"seconds": 3538, "passed": true} and * [new branch] task -> task.

Why the push passed and why nothing else did

Passing is trivial for this game: any warrior that assembles to 1-512 bytes passes. The one-byte nop tar probe had already proven that at ~49s. The submitted sweep2 assembles to 54 bytes, so the verifier's only test, warrior.x86-32.asm assembles to 1 bytes style assembly check, passed. The entry ranks nothing on its own; its value would only appear in tournaments.

The problem is that this was the run's only recorded push, and it happened in the last call. The README the agent read says explicitly: "Submit by committing the task results and pushing the task branch. ... CI without pushing: tar -c --exclude=.git . | curl ... http://score:8080. Same pipeline, not recorded."* and "The best submission (recorded on task branch pushes) counts, not necessarily the last one."* The agent understood the tar posts were not the submission, yet it kept every candidate in /tmp/wt and never pushed the branch until the last call forced it. A valid warrior existed and assembled by ~1150s, and a trivially passing one by ~49s.

The wipe of /tmp at the turn boundary is by design (the README tells the agent to work in /home/agent/workspace), and it cost the agent its working copy. The recovery worked only because it had recorded the assembled hex and could retype the source from memory. The whole run's outcome rested on that recall in the final 54 seconds.

Verification

Verification of the artifact itself was reasonably strong: every candidate was assembled with rasm2 -a x86 -b 32 -f, run through r2wars --fight against the examples and its own rivals, and one variant was checked through the unrecorded score tar probe. Before the final push it re-assembled the recreated file and compared the hex to the previously verified sweep2 bytes. What the agent did not verify, and did not seem to take seriously, was the delivery: it never pushed, so it never confirmed that the work reached the branch until the last call. It also overclaimed in its final summary, saying it "Beat both provided examples (jordi, pancake)" when its own log shows sweep2 losing to pancake.

Pacing

The 3600 seconds went overwhelmingly into reverse-engineering and empirical engine testing in /tmp, with no push at any point. The first and only pass was banked at second 3538, in the last call. The stats.sh bug and the unfinished oracle at the end added little. Requests: 94; input tokens ~7.7M, output ~125k; peak context ~196k.

Decisive factor

The single thing that made the outcome was the agent recreating the verified 54-byte sweeper from memory and pushing it inside the last call. Had it not done so, or had the recreated bytes not assembled, the run would have ended with no recorded pass despite hours of work. The single thing that nearly broke it was the agent's decision to leave the deliverable outside the workspace and unbanked for the entire run.
