r2wars-x86-32: bidirectional carpet-bomber

The task and the bar it is graded against

The task (task.md) asks for warrior.x86-32.asm, an x86-32 warrior that rasm2 -a x86 -b 32 -f assembles to at most 512 bytes, and says "Write the strongest warrior you can: locate the opponent, overwrite it, survive." The verifier is much weaker than that goal: per games.md, "The verifier assembles the warrior with rasm2 ... it has to assemble to 1 to 512 bytes. A warrior that assembles passes. Passing is all there is to rank on its own, the fights are what tells warriors apart." So the recorded pass depended only on delivering a well-formed file to the task branch; strength would only matter later, in a tournament of entries, and this run was not a tournament.

Turn 1 (uuid 21e5aedf): reconnaissance, design, one push

The first harness turn ran about 1776 seconds (59 model turns). The agent read README.md and task.md, then explored the sandbox: /opt/r2wars/README.md, the two bundled examples under /opt/r2wars/examples/x86-32/ (jordi, pancake), the r2wars launcher script, and strings/binary inspection of /opt/r2wars/bin/r2wars.dll. It found the round cap empirically by fighting two passive warriors to a standstill: round 1: timeout after 50001 cycles ... draw, and strings ... MAX_CYCLES.

It then probed the assembler itself. A candidate using labels produced a jump to the wrong address; the agent disassembled and compared:

[TOOL_RESULT ...] 81e6ff030000ebff90f4
0x00000006   2    ebff  jmp 7
0x00000008   1      90  nop
0x00000009   1      f4  hlt

The branch should have reached the hlt at 0x09, but landed at 0x07. The agent concluded rasm2 mis-encodes forward label branches and worked around it by using numeric absolute targets everywhere, verifying each one against rasm2 -D. This is recorded in the final file's header and is a genuine, correctly diagnosed tooling quirk.

The design settled into a bidirectional carpet-bomber: locate itself with call getpc; getpc: pop ebx; sub ebx, 5, then sweep a forward pointer from ebx+68 upward and a backward pointer from ebx downward, both wrapping through the 1024-byte arena with and X, 1023, writing 0xF4 (hlt) into every byte and skipping the code region by comparing each pointer to ebx. The rationale is sound for this game: any opponent whose PC lands on a poisoned byte dies regardless of its register state, and the self-skip avoids suicide.

Candidates were fought with a runmany.sh harness against jordi, pancake, a passive nop; jmp opponent, and self-play. The final 66-byte version assembled byte-identically to the tested /tmp/w7.asm:

Why it passed

The push passed because the warrior assembles to 66 bytes, comfortably within 1–512, and the verifier checks nothing else. The pass was banked at 1602s, ~44% into the 3600s budget, and the commit was never overwritten. The only real threat to the outcome was not the warrior's quality but the possibility of ending the run without a valid file on the branch (for example tagging release before the first push); the agent avoided that. Its later variants also assembled, so they would have passed too — but leaving the tested commit in place was the safe choice.

Assessment

The engineering was careful: environment reconnaissance, a real assembler defect found by disassembly, a design whose failure mode (self-overwrite, timeout) was explicitly tested, byte-level verification before pushing, and the CI pipeline exercised locally. The waste is that turns 2 and 3 optimized a fighting strength that this run's verifier does not measure, against two bundled examples that are not the tournament field, and no variant was better. That is speculative effort, not an error that endangered the pass, and the agent correctly stopped and released rather than spending the remaining ~680s.
