chess-vm run analysis

Task and setup

The agent had to write bot.cvm, a move-scoring policy in the CVM assembly language, and the game rates a submission by playing it against a 27-opponent field. prepare() runs a round robin once per scoring container to rate the field, and after that every push is scored in seconds against the cached ratings. The task's own README warns the round robin takes minutes and that the default 300s budget is too short, hence the 3600s budget on this run.

What the agent did, in order

  1. Read the spec (SPEC.md, README.md, task.md, the starter bot.cvm) in the first two tool calls.
  2. Wrote a first policy (index 17): mate-in-1, static-exchange-eval, promotion, check, center control, mobility, opponent mobility with a stalemate-avoidance branch, and an "exposed piece" penalty — 28 instructions. It tried to submit by piping tar | curl to score:8080 directly in the foreground.
  3. Hit the environment's first-request cost: the Bash call exceeded the default 120s timeout and was silently backgrounded; the agent's own follow-up sleep 100; cat ...output (index 30) returned scoring timed out. The proxy log confirms this was a real HTTP 500 after 147.9s — the scoring container's opponent-field round robin (prepare()) had not finished when the request landed, exactly the slow-first-push behavior the task's README documents. This cost the agent a detour (background + a 100s sleep) rather than the run, since it correctly diagnosed the situation and moved to git push with a generous timeout next.
  4. Banked the first pass at 254s: git push origin task scored rating 887 (bot.cvm has rating 887, the field ranges from 0 to 1201), confirmed again with a direct local score call.
  5. Built a local dry-run harness (/tmp/t.sh): copy a candidate file to a scratch dir, tar+curl it to score:8080, grep the reason/error line. This let it compare weight variants against the real field without recording a graded attempt for each one — the key enabler of the whole run.
  6. Iterated on features and weights, evaluating locally before committing:
    • Added a "hanging piece" detector (attackers vs defenders per square) — 962.
    • Tried castle bonus (939), pawn-advance-by-rank bonus (1052, kept), king-move-early penalty (957, dropped).
    • Swept the pawn-advance weight: 8 -> 1037 (w=16), 1080 (w=30), 1087 (w=60 and w=100, plateaued) — banked the second pass at 374s with rating 1087.
    • Swept mobility weight (1107 at x3, 1039 at x0, 1129 at x6, 1055 at x12) and center weight (1026 at x15, 1107 at x1), then rewrote the hanging-piece logic into a signed "threat" term that scores both hanging own pieces and attackable enemy pieces, sweeping its weight (1163 at x1, 1232 at x2 sic — actually see below) and the hang-penalty weight (1098 at x15, 1125 at x7) — banked the third pass at 464s, rating 1169.
    • Swept threat weight again: 1163 (x1), 1232 was actually the thr3 variant at weight x3 which the agent committed and banked the fourth pass at 551s, rating 1232.
  7. Kept exploring after the last banked push, evaluating opponent-mobility weight (1193 at x5 vs the current x2), check-bonus weight (1237 at x100, notably higher than the banked 1232), an exposed-piece penalty (1121), and SEE weight (1172 at x14) — none of these were committed.
  8. Explored a further round (chk200: 1186, opp1: 1205, kingdist term: 1229, enemykingdist term: 1210) — still none committed; kd at 1229 came close to but did not beat the banked 1232, but chk100 from the round before (1237) did, and was never revisited or reapplied.
  9. Ended the run: git push -q origin task (a no-op re-push of the already-banked thr3 commit) followed immediately by git tag release && git push origin release, which the book documents as an explicit early end to the run. This happened around 566s into a 3600s budget.

Why the pushes passed

All four pushes passed verification outright — bot.cvm produced a score for every decision (no faults, no cycle-budget overruns), which is the only way a chess-vm push fails outright. Rating is derived from performance against the field, not a pass/fail threshold, so every attempt in the log is "passed": true with an increasing rating; there was no near-miss or rejected push at any point.

Assessment

The agent's local dry-run loop is a strong pattern for a field-rated game: it let a single 3600s budget produce four increasingly good banked entries from perhaps 15-20 total field evaluations, most of them free of the cost of a recorded attempt. The one blemish is that it stopped exploring and tagged release right after finding a strictly better configuration (chk100, 1237) than what was on the branch (1232), and never looped back to commit it — a small, avoidable loss given that 84% of the time budget was still unused. The single environment hiccup (the first score POST failing with a 500 while the field's round robin was still warming up) is documented behavior of the game rather than a bug, and the agent absorbed it without real cost to the outcome.
