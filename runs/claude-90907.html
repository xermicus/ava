Task and constraints

The task is chess-vm: write bot.cvm, a single-move scoring policy in a tiny register VM with no search, memory, or stack. The verifier plays the submission against a fixed field of 27 CVM opponents (20 games each, alternating colors) and reports a rating; a program that faults on any decision fails outright. The book notes the default budget is too short for this game and that iteration against the field "takes hours" — this run had 5400s (1.5h).

Turn 1: orienting and finding the fast loop

The agent read README/task/SPEC, checked git history and the score/git proxy hosts, and — critically — discovered it could tar the workspace and POST it to http://score:8080 to get a full verified rating without touching git:

"CI is fast (~1.3s), so I can iterate empirically. Let me set up a submit helper and build a first real bot."

This is the single most consequential decision in the run. The book describes score as exactly this: a verify-without-recording endpoint meant for fast local iteration, as opposed to git push origin task, which is verified and kept as an entry. The agent used score 947 times over the run and git only 10 times (2 real pushes plus a handful of git log/ls-remote checks), matching the intended design of the benchmark.

Its first hand-written bot (MATERIAL + GAIN + GIVESCHECK) scored 619 against a random-mover baseline of 316. From there it wrote exp.py/run1.py...run11.py to grid-search term inclusion and weights: material-only was strong, SEE, EXPOSED, MOBILITY stacked to 905, then 920, then 945.6 after narrowing the mobility coefficient.

Coordinate descent and a self-inflicted setback

The agent then wrote a background coordinate-descent script (cd.py) and ran pkill -f cd.py moments after starting it to restart it with fixes — the pkill also killed the shell that was still writing the script via heredoc:

"The pkill killed my shell before writing the file. Let me move scripts out of the workspace and rewrite."

It recovered by relocating all its Python tooling to /home/agent/work (outside the scored workspace) and continuing. This cost some wall-clock time and script-rewriting but had no lasting effect on the outcome — a clean example of an agent-caused problem that stayed self-contained because the actual submission artifact (bot.cvm) was never affected.

It also tested whether concurrent submissions to score sped up iteration; the server serializes requests, so that avenue was correctly abandoned rather than wasted on further parallel-request engineering.

The structural jump: piece-square tables

After weight tuning plateaued near 945–966, the agent judged that piece-square tables would be "a bigger win than weight tuning" and built a PST generator (gen2.py). Its first attempt had an indexing bug:

"PST index off by one — need kind-1. Let me fix."

caught only by inspecting behavior, not by any pre-submission check — every "check" in this run was simply the score/rating itself, not code review. Once fixed, PST alone drove the rating to ~965, then to 994 combined with a from-square PST ("true delta" for piece movement), then ~1007 after further weight tuning around the PST.

The end of the run

No further push occurred, but none was needed: nothing in the tail of score.error.log after the 1119 push shows a stable configuration clearly and repeatably beating 1119 — round-1 values fluctuate between roughly 770 and 1100 as the search explores, so no better result was left unbanked.

Why it passed, and why it scored well

Both pushes passed cleanly (0 faults, 0 cycle budget overruns in both cases per score.error.log), because the agent never submitted anything to git that it hadn't already verified via the score endpoint immediately beforehand. The final rating (1119 of a field ranging 0–1201) reflects genuine, well-tested improvement, not a fluke — it is the product of a large number of cheap, correctly-interpreted empirical measurements rather than of any chess domain knowledge coded up front.
