Task

The game is chess-vm: write bot.cvm, a one-ply, no-search move-scoring policy in a restricted CVM assembly (16 registers, no writable memory, no stack, 256 instructions / 1024 data words / 20M cycles per decision). The engine scores every legal move once and plays the highest scorer; the field is 27 built-in opponents including up to a 4-ply searcher rated near 1201, so a one-ply policy has a hard ceiling well below the top of the field.

What the agent did

The agent (deepseek-v4-flash, high thinking, under Claude Code harness) opened by checking for existing CVM tooling, found none, and went straight to writing a first policy combining material, mobility, king-safety and tactical terms, submitting it through the CI scoring endpoint before committing anything to the tracked branch. That baseline scored 688.

It then ran a long hill-climbing loop for the rest of the 3600-second budget: pick one lever (a feature's presence, or one weight), test it via CI, keep it if the rating rose, otherwise restore the last best version (tracked in git as a running sequence of v1...v137). The rating climbed in a long staircase:

688 → 813 → 832 → 841 → 847 → 854 → 867 → 879 → 880 → 881 → 882 → 886 → 896 → 898 → 902 → 903 → 907 → 909

Key turning points, each confirmed by the agent's own commentary:

  • v3 (832): richer tactical policy — added EXPOSED/HANGS penalties and king distance.
  • v12 (841): mobility 18 + check 50 — first committed, pushed submission (second 257, rating 841.26 per score.log).
  • v18/v23/v27 (847→854→867): pawn-push weight 30, check weight 70, enemykingdist 12 — three real single-weight wins in a row.
  • v40/v45/v51 (879→880→881): safe-capture bonus (+70), safe-check bonus (+50), check weight retuned down to 40 alongside safe-check.
  • v58 (882): a check-and-capture combo bonus.
  • v68/v76 (886→898): opening move-count penalty (discourage re-moving the same piece before ply 18, −25) and an early-queen penalty (−30 before ply 8) — the agent explicitly flagged the early-queen change as "the biggest single gain this round" (+10).
  • v110 (902): a KINGDIST term (Chebyshev distance between the two kings) rewarding closing distance to the enemy king, weight 5.
  • v135/v136/v137 (903→907→909): a castling bonus, eventually settled at +200 for castling any time before ply 40 — the last and second-largest structural win of the run.

Alongside these wins, the agent tried and correctly rejected dozens of ideas that looked plausible but measured worse: doubling material weight, passed-pawn bonuses, center-control bonuses (opening and middlegame), endgame branches (material-gated promotion/king-centralization), development/tempo heuristics (movecount bonuses, minor-piece development, rook-pawn penalties), "avoid trades when ahead", asymmetric mobility, aggressive blunder-avoidance rescaling, and fine multi-weight combination searches around already-tuned values. It used this negative evidence appropriately — reverting to the last best committed version (via git checkout) before each new experiment, so the tracked branch never regressed.

What passed and why

Every one of the 12 recorded pushes in score.log passed (passed: true); this is a rating-based game with no fail state short of not pushing anything, so the entire question is how high the rating climbed. The final and best push (909.44, second 2913) matches the agent's own final summary and the last committed commit it verified (9286fa2, v137). The rating trace in run.json's attempts list matches the agent's self-reported progression exactly, confirming the agent's tracking of its own progress was accurate throughout — it never mis-stated what was actually recorded by the verifier.

What went wrong (agent-caused)

The overwhelming majority of the run's 13 harness turns (per monitor.json, turn: 14, elapsed_seconds: 3542 of limit_seconds: 3600) were spent on tuning that had already been shown not to matter. From roughly rating 867 onward, the agent repeatedly re-tested weights it had already fixed (enemykingdist at 11/13/14, check at 30/50/60, safe-capture at 50/60/80/90/100, hangs at -150/-250/-300/-400, exposed at -100/-140/-160) across many separate turns, each time confirming the existing value was optimal without learning anything new. This is legitimate as isolated experiments but wasteful in aggregate — a large fraction of the ~57.8M input tokens and $200+ of usage (per-turn result events show costs from $6 to $51 each, totalling roughly $275) bought confirmations rather than gains.

A second, more concrete inefficiency: in at least two stretches (around v110→v135 and again around v137) the agent's own text output degenerated into dozens of consecutive one-line turns like "Let me restore v137." / "Let me do it." — a sign that a single logical action (git checkout + sed + rerun CI) was being narrated turn-by-turn rather than executed in one composed step. This did not stall progress (the rating kept moving in the surrounding turns) but it is a clear efficiency defect: a smarter harness loop would have batched the restore-edit-test cycle into fewer, more information-dense turns.

The run ended via the harness's normal last-call mechanism, not a crash.

Verdict

This is a clean pass driven entirely by the agent's own design and tuning discipline. It banked early, iterated safely (always testing before committing, always reverting on a worse result), and found several genuine, well-reasoned improvements (opening development heuristics, king-distance, castling). Its main defect was efficiency, not correctness: a large share of the budget was spent re-confirming already-settled parameters rather than searching for new structural ideas, and some turns were spent narrating trivial mechanical steps one at a time instead of composing them.
