What happened

The task: write bot.cvm, a CVM assembly move-scoring policy for chess-vm, and get it rated against a 27-bot field (0-1201 rating range). The agent read SPEC.md, tried a literal copy of the README's example (MATERIAL/GAIN/SEE/MATEIN1), and used it to learn the submission channel available in the sandbox: a curl-a-tar-to http://score:8080 helper (submit.sh) that returns a verdict JSON.

Per the book (architecture.md, games.md): "The score host on the same socket verifies a posted tar without recording it"* — only a git push to the task branch, served by the git host, creates a recorded, ranked entry. The proxy access log shows the agent hit score 19 times over the run and git only twice: a clone at the very start (15:28:20) and exactly one git-receive-pack at 16:33:22, roughly 70s after the 3600s budget elapsed (monitor.json: last_call:true, elapsed_seconds:3750). That single push is the only entry ever recorded (entries/3890/bot.cvm, run.json attempts: one item, passed:true, rating: 813.41741370781).

Building a strong policy, entirely off the books

Score-log (score.log/score.error.log) shows the agent iterating rapidly through the free score endpoint:

  • 15:29:38 — 3-instruction stub, rating 316, passed
  • 15:31:12 — 10-instruction stub with PST scaffolding attempt, rating 813
  • 15:34:41 — a bad register operand ('8' is not a register) failed the push
  • 15:35:38/15:39:52 — a 41-instruction PST version faulted 18601 decisions with LD read data address 460, outside 0..448 (out-of-bounds data read), rating 429 but failed (a program that faults never passes regardless of rating, per games.md)
  • 15:42:54 and again at 15:42:55 (agent log) — the fixed 42-instruction version, "v2.cvm", scored 925.30, described in the agent's own words: "925. Let me build a sweep driver to tune terms automatically."

v2.cvm's eval combined material, SEE, mate-in-1, king exposure, center control, mobility, opponent mobility, check/castle/king-safety bonuses and a piece-square table generated by a Python script (gen.py). This is real engineering work and it produced the best result seen anywhere in the run — nearly 100 points above what was ultimately banked.

The tuning phase that undid it

From 15:43 to 16:23 (40 minutes, most of the run) the agent tried to improve on 925 with automated sweeps (sweep.py, then a parallelized psweep.py). This phase was unproductive: an ablation sweep script had to be rebuilt after argument-passing bugs (FileNotFoundError from passing JSON as a shell heredoc file instead of a literal), and no logged sweep result beat 925.

At 16:11:08 the agent ran a concurrency smoke test, not a tuning step:

for i in 1 2 3 4; do (./submit.sh v1.cvm > c$i.out 2>&1) & done; wait

submit.sh's first line is cp "$1" /home/agent/workspace/bot.cvm before it tars and posts. Running it on v1.cvm — the old crude baseline, not the tuned v2.cvm — overwrote the real workspace file, /home/agent/workspace/bot.cvm, with the inferior version (rating ~813-818). This was a side effect the agent did not appear to register; its text output after this ("Sweep works (6s/eval). Let me test concurrency then run coordinate descent.") does not mention having just replaced the workspace's best file with a worse one.

The agent's next and last visible action, 16:23:12, tested v2.cvm again but by copying it into a scratch tt/ directory and curling straight from there — this verified v2 still scored well, but never touched /home/agent/workspace/bot.cvm, so the clobbered v1 stayed in place. The tool call was started as a background task (task_started) and its result never appears in the log; the session log shows repeated system init restarts clustered right after this point (indices 5003, 5041, 5043 in a ~5044-line log), coinciding with proxy.error.log entries like unexpected DNS response for llm.substrate.dev recurring from 15:33 onward and intensifying late in the run. The agent never got, or never took, another turn to check and fix the workspace file.

What got banked

Because the agent never pushed to git during the run itself, the single automatic/forced push that happened during the last call (16:33:22) submitted whatever sat in the workspace at that moment — the clobbered v1.cvm, rating 813 — instead of the demonstrably stronger v2.cvm at 925. The run is recorded as a pass, but at roughly a third less of the achievable rating margin (813 vs 925, against a field spanning 0-1201).

Environment context

proxy.error.log shows recurring unexpected DNS response for llm.substrate.dev and duplicate-header warnings on the LLM upstream from 15:33:58 onward, worsening in the run's second half (multiple bursts through 16:10-16:31). agent.log shows the harness session re-initializing far more often (8 times) in its last ~800 lines than earlier, suggesting these backend hiccups were costing the agent turns/continuity right when it needed to notice and repair the workspace-file mistake. This did not prevent a pass, but it plausibly closed the window the agent would have needed to catch its own error.
