What happened

The task (chess-vm) asks for bot.cvm, a one-ply move-scoring policy in a small register assembly language (CVM), scored by its ELO-style rating against a fixed field of 27 opponents ranging up to a 4-ply searcher (rating 1201).

Discovery phase

The agent read README.md, task.md and SPEC.md, inspected the existing bot.cvm in the workspace, and noticed there was no local assembler or chess engine available. Rather than blind-pushing, it tried the score:8080 endpoint directly:

timeout 300 bash -c 'tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080'

This is the score host described in the book's architecture chapter — "verifies a posted tar without recording it" — and it gave the agent a full rating verdict without needing a graded push or leaving an entry. This was the single most consequential move in the run: it converted the task from "guess a policy, push, wait" into a fast local optimization loop.

First working bot

It wrote a Python CVM assembler (asm.py) to catch syntax errors locally, then hand-wrote a policy combining MATEIN1, SEE, PROMO, MOBILITY/OPPMOB, GIVESCHECK, CENTER, ISCASTLE, EXPOSED, and king-distance terms. The very first draft jumped the rating from a random baseline of 316 to 947 (log lines 27-32).

Tuning loop

It then built a config-driven generator (gen.py, later gen2..gen5.py) and a run.sh/eval.py harness to sweep weights against the score endpoint, iterating through many small experiments: okd=1 (own-king-distance) unexpectedly gave a big jump to 1109 once ekd/kd were already tuned (line 109), castle=80-100 and check=0 (dropping the give-check term) squeezed out further gains to ~1121 (lines 137-153). Piece-square tables were tried twice (gen2.py, gen4.py) and both times made the rating worse, so the agent correctly dropped them rather than forcing a structural idea that wasn't paying off.

Its own bug cost time

Between lines 90 and 105, the agent's rewritten generator (gen3.py) produced a materially different rating (668 vs. the expected 1060) for what it thought was the same configuration. It spent several turns diffing gen.py against gen3.py before finding the actual bug: it had added exposed and ekd with ADD instead of SUB, flipping their sign. This is a self-inflicted debugging detour, not a benchmark or harness problem — the toolchain the agent wrote its own tests against was buggy, and it didn't catch this before running dozens of sweep configurations under the wrong semantics.

Search automation and the final push

Near the end, the agent wrote search.py for coordinate descent, which found check=5, castle=90 → rating 1130.8, its final committed value, pushed at 3251s. It then wrote randsearch.py for a broader random-restart search, but time ran out (the 3600-second budget) before it produced any result — log line 185 even shows the agent noticing "No output yet after 5 minutes?" while waiting on it, then giving up. The last call (log lines 195-205) simply confirmed the working tree was clean and the already-pushed 1131 bot was the one on the task branch; no new work happened in the last call.

Why the pushes passed

Every one of the four attempts (861s: 1061, 1257s: 1115, 1874s: 1121, 3251s: 1131) passed cleanly — bot.cvm has rating N. This is a game with no failure mode besides a faulting/cycle-exhausted program (which forces the first legal move and fails the push); the agent's programs always produced a SCORE for every decision, so nothing ever failed the assembler or cycle budget checks. Because the agent tested every candidate against the score endpoint before committing, it never pushed a config that scored worse than its running best.

Assessment

This is an unambiguous, clean pass with real, measurable improvement across four banked pushes (316 baseline → 1061 → 1115 → 1121 → 1131, against a field topping out at 1201). The agent's process was sound: fast feedback loop, systematic weight sweeps, dropping ideas that didn't pan out (PST), and banking every improvement immediately rather than risking an unbanked final push. The only real blemish is time lost to its own generator bug and a final search that never finished — neither changed the outcome, since the best-known bot was already committed well before the clock ran out.
