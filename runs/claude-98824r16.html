chess-vm run analysis

Task and mechanics

The task asked for bot.cvm, a chess move-scoring policy in the CVM assembly language (16 registers, no memory/stack, chess-reading instructions like SEE, ATTACKERS, MOBILITY). The verifier plays a submission 20 games against each of 27 built-in opponents (ratings 0–1201) and records the rating in the push's verdict; the best-rated push counts, not the last one. A score-only endpoint lets the agent run the same verifier without recording a result, which is the sweep instrument the agent leaned on throughout.

Turn-by-turn

Turn 0 (0s–~1773s). The agent read the task, discovered a random-mover baseline rated 316, and set out to write a real evaluation: material, SEE-based exchange loss, a hanging-piece scan, threat detection and PSTs. It built the policy through a Python generator/template pipeline in /home/agent/gen (outside the repo) rather than hand-editing the assembly each time.

At 315s it pushed its first real policy and banked a passing rating of 1092 ("Committing and pushing it so there's a recorded submission" — correctly treating a bank as insurance against running out of time later).

It then rewrote the hanging-piece detector to use a proper least-valuable-attacker (LVA) scan with x-rays, and re-tuned the check-threat weight (CHKTHR). It validated this with an 8-seed sweep before committing:

"CHKTHR=12 holds up under the noisier jitter too (+36 over 8 seeds). Pushing that version (1241 without jitter)."

The push at 1773s scored 1235, beating the strongest of the 27 built-in opponents (1201). This is the push that ultimately decides the outcome.

Turn 1/2 (1773s–3492s). The agent explored further additions: a second hanging piece term (LOSS2), a pawn-push bonus when ahead (PPUSH), and king safety (attacks on the king zone plus a pawn-shield term scaled by game phase). It logged that LOSS2/PPUSH were within noise, then swept king-safety parameters over 4–8 seeds each:

k [KZ=5] mean=1160.5 sd=31.8
k [KZ=10] mean=1157.1 sd=30.3
k [SH=10] mean=1193.1 sd=30.6
k [KZ=5 SH=10] mean=1187.3 sd=18.2

None of these tested combinations beat the already-banked 1235, and the sweep itself was run on a different code branch (with an added king-square encoding and other structural changes) than what eventually shipped, so it was at best a weak signal for the final composite.

In parallel, the agent launched a background sub-agent at 13:46 (about 11 minutes of the 60-minute budget remaining) to build a local Go chess simulator with a full legal-move engine, so it could see why particular games were lost rather than only the aggregate rating. This was reasonable in principle but started far too late; it "didn't finish before time ran out," so the final push was still decided from aggregate ratings alone, per the agent's own closing report.

Final push (3492s, inside the last-call turn). The agent generated the build with python3 gen.py SH=10 LOSS2=3 TRADE=2 — note KZ is absent and so falls back to its template default of 0. The shipped assembly contains:

kzdone:
    MULI r3, r11, -0

which always zeroes r3 regardless of r11 (the counted king-zone attackers), so the "king safety" term the agent had been sweeping was dead code in the shipped build — present, consuming cycles, but contributing nothing to the score. Unlike every earlier change, this one was committed and pushed straight from generation, with no CI-only score check first. It scored 1213, below the 1235 already on record.

Why it passed anyway

chess-vm's scoring rule keeps the best-rated push as the entry of record. Because the agent banked 1235 at the 1773s mark — well before the deadline, and via a properly validated change — the final, unvalidated regression at 3492s does not change the outcome. The agent's own closing summary correctly states this:

"Since the best push counts, 1235 stands."

The agent did not tag release, reasoning the solution likely wasn't saturated, which is a defensible call given the remaining, still-untested experiments.

Assessment

This is a clean pass, with the winning margin coming entirely from disciplined, noise-aware iteration in the middle of the run rather than from the final push. The one clear misstep — shipping a bundle of three new terms including a mis-generated, always-zero king-safety weight without a single CI check — happened under self-imposed last-call time pressure and cost nothing only because the scoring rule protects against exactly this kind of late regression. The late-started local simulator sub-agent is a secondary miss: had it been launched earlier in the run, the agent might have replaced blind rating sweeps with example-level debugging and pushed the final rating meaningfully higher.
