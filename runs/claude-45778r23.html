What happened

The task (chess-vm) asks for bot.cvm, a one-ply CVM move-scoring policy compiled against SPEC.md, judged by its Elo rating against a 27-bot field (games/chess-vm). The README explicitly tells the agent it can validate a candidate for free via tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080 — "Same pipeline, not recorded" — before spending a real push, and that only the best recorded push counts.

Opening move

On its very first tool call the agent read README.md/task.md/SPEC.md and inspected the starter bot.cvm (36 bytes, essentially a stub). It wrote a policy combining material, static-exchange evaluation (SEE), a check bonus, a castling bonus, mobility differential, center control, a hanging-piece penalty, a destination-square safety margin, and a king-hunt term gated on material advantage:

MULI r2, r2, 4          ; SEE: exchange safety
MULI r3, r3, 35         ; bonus for giving check
MULI r5, r5, 30         ; bonus for castling
SUB  r6, r6, r7 / MULI r6, r6, 6   ; mobility - opponent mobility
MULI r8, r8, 5          ; centrality
MULI r9, r9, 4          ; penalty for leaving a piece hanging
MULI r10, r10, 30       ; bonus if destination is defended enough
...
LDI r13, 500 / JLE r1, r13, skip_hunt   ; king-hunt only when ahead on material

It tested this against the unrecorded endpoint first ("Now let's test it with the CI-without-pushing endpoint before committing"), got a rating of 916, then committed and pushed. score.error.log shows the verifier accepted it immediately: "bot.cvm has rating 916, 0 faults, 0 cycle budget overruns" at 12:55:04Z, 128s into the run — score.log/run.json.attempts recorded this as the first passing push.

Iteration loop

From there the agent ran a disciplined hill-climb, visible turn by turn in its own narration:

  • "Small improvement (916 → 928). Let me push this and keep iterating."
  • "Improvement (928 → 955). Let me push this and continue tuning."
  • "That's worse — revert to the previous weights." (a regression caught and discarded before it ever reached a real push)
  • "Good improvement (955 → 984)."
  • "Slight improvement (984 → 987)."
  • "Better still (987 → 1000)."
  • "Improvement (1000 → 1017)."
  • "Improvement (1017 → 1026)."
  • "Marginal improvement (1026 → 1028)."

score.error.log records 33 "passed" verifications total against only 9 lines in score.log — the gap is exactly the free score:8080 trial runs the agent used to screen candidates (including some that scored worse, e.g. 877, 915, 950-958, never pushed) before committing to a real push. Every one of the 9 recorded pushes (score.log, matching run.json.attempts) was a strict improvement over the last: 916, 928, 955, 984, 987, 1000, 1017, 1026, 1028, banked at seconds 128, 174, 225, 294, 372, 438, 499, 559, 591 respectively. Nothing was ever pushed that regressed the recorded entry.

Ending the run

After the 591s push (rating 1028), the agent tried further single-parameter perturbations, found they "consistently regressed," and concluded: "This looks saturated for weight tuning on this feature set, so I'll tag a release." It ran git tag release && git push origin release, and the remote replied "release received, the run ends." run.json shows finished_seconds - started_seconds = 1790341547 - 1790340783 = 764 seconds — about 12.7 minutes total, against a 3600-second budget. The agent chose to stop with roughly 78% of its time budget unused rather than continue tuning a saturated feature set, a defensible call given the marginal per-push gains had shrunk to single digits (1026 → 1028).

Environment

proxy.access.log shows only one non-200 request to api.anthropic.com: a 499 (client closed connection) at 13:05:47Z, the same instant as the release push — the harness cancelling the in-flight connection because the run had just ended, not a backend fault. metrics.failed_requests/aborted_requests are both 1, consistent with this single benign cancellation. No faults, cycle-budget overruns, or verifier errors appear anywhere in score.error.log, and proxy.error.log/monitor.json show nothing abnormal beyond routine nginx buffering notices.

Verdict

This is a clean pass with no failure mode to name. The decisive factor was procedural discipline: using the free, unrecorded scoring endpoint to gate every push meant the agent's real submissions only ever moved the rating up, so the best entry (1028) was both the highest and the last recorded push, banked over 3000 seconds before the deadline. The only thing left on the table is a higher ceiling from a richer evaluation function, which the agent correctly identified as outside the reach of further weight tuning on the feature set it had chosen.
