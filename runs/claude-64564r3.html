What the agent set out to do

The task (chess-vm) asks for bot.cvm, a move-scoring policy in a restricted assembly language (16 registers, no memory/stack, 256 instructions, 1024 data words, 20M cycles/decision, no search). The engine scores every legal move once and plays the highest-scoring one, so the whole task is designing a good static evaluation function and expressing it in ~20 instructions.

The agent's first turn (line 2089 of agent.log, 11:06:40) contains a long, competent planning think: it reasons about cycle budgets (20M/decision ≈ 500K/move, trivial for a handful of chess primitives), about MATERIAL + SEE approximating a 1-ply-plus-recapture evaluation, about mobility terms, about MATEIN1 as a large mate bonus, and about whether a full piece-square-table loop over 64 squares would fit the instruction budget. It explicitly noted the killer feature of this task: README.md line 9 says CI can be run unrecorded via tar ... | curl ... http://score:8080 — "Same pipeline, not recorded." The agent leaned on this hard.

Why the push passed

The committed bot.cvm is 21 instructions: MATERIAL, 5*(SEE-GAIN), MOBILITY, -OPPMOB, MATEIN1*100000, -EXPOSED, summed and returned via SCORE. The round-robin breakdown logged at verification time (score.error.log, 12:04:58) shows why the rating lands at 968: near-perfect scores against weak/heuristic opponents (random 20-0, cccp 20-0, min_opp 20-0, alphabetical 20-0, pawnstorm 20-0) and heavy losses only to the search-based opponents the one-ply eval structurally cannot beat (steady 0-16, sensei 3-16, composite 1-14 draws-heavy, positional mostly draws). This is a reasonable, well-tuned one-ply policy that sits in the upper half of a 0-1201 field.

What the agent got wrong

The agent's own instructions (README.md, read at the very first turn) told it to bank a first passing submission and only then keep improving. It instead spent the entire budget doing local, unrecorded iteration and pushed to git exactly once, at the very last possible moment its main turn allowed. The margin it left itself was razor-thin: had tune8.py's last sweep round taken another minute, or had the final tools/cvm.py check plus score:8080 confirmation plus git push taken more than the roughly 20 seconds they consumed, the whole run would have ended with zero pushes and a failing ("never pushed"/unbanked-shaped) outcome despite a genuinely good solution sitting in the workspace the whole time. The run's monitor.json confirms the mechanism that rescued it: elapsed_seconds 3541 with last_call: true on turn 2 — the harness had to forcibly end the agent's overlong turn and grant it a fresh, time-boxed final turn to get anything submitted at all.

Bottom line

The modeling and empirical tuning work is genuinely strong — a 316→968 climb with careful cycle/instruction bookkeeping and systematic A/B sweeps. But none of that would have counted for anything without the last-call mechanism, because the agent treated "push early, iterate later" guidance as optional and left submission to the last seconds of a self-inflicted single marathon turn.
