Chess-VM run analysis

Task

Write bot.cvm, a one-ply chess move-scoring program in a restricted VM assembly (16 registers, no writable memory, no stack, no lookahead, 256 instructions / 1024 data words / 20M cycles per decision). The engine scores every legal move once with the submitted program and plays the highest score; verification plays 20 games against each of 27 built-in opponents (rating field 0-1201) and reports a rating.

Turn-by-turn

Turn 1 (agent.log lines 1-77, 647k input tokens, no git push at all). The agent read README.md, task.md, and SPEC.md, reasoned carefully about the instruction set (correctly working out that MATERIAL after a move doesn't see the opponent's reply, so hanging a piece to a quiet move isn't penalized by material alone, and deriving MATERIAL + SEE - GAIN as an exchange-safety term that avoids double counting captured material). It then tested designs exclusively through the unrecorded endpoint:

tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080

going from a random-mover baseline (rating 316) to a first real eval (MATERIAL+SEE-GAIN+mobility+EXPOSED+CENTER+GIVESCHECK, rating 957), then adding a piece-square table for the destination square (rating 1003 once two assembler bugs were fixed: MOD r13, r12, 8 used an immediate where MOD requires a register, and the PST addressing forgot to reserve a block for piece-kind 0, producing a fault reading data address 396 outside the 0..384 table). It built a Python generator (gen.py) to parametrize weights and ran two rounds of one-parameter-at-a-time sweeps (sweep.py, sweep2.py), converging on w_exp=2, w_center=0, w_mob≈5, w_check≈30. All of this — the entire first third of the run's time budget — never touched git. Had the run ended here, score.log would have zero entries despite a functioning ~1000-rated bot already existing in the untracked workspace.

It correctly recalled the best-known result from its own sweep log rather than trusting whatever half-finished file was left on disk, regenerated the kd5 configuration, pushed it — the pipeline confirmed rating 1062.2 at 3518s — and then tagged and pushed release, ending the run voluntarily at roughly 3537s, well inside the 3600s limit and without needing the forced last call.

Why it passed

Every attempt on the tracked branch passed (1041, 1049, 1062), each better than the last, and the run ended by choice. The eval design itself was sound: MATEIN1 dominance, SEE-based exchange safety, mobility difference, a proper piece-square table, and a late king-danger term, tuned empirically against real measured ratings rather than guesses.

What actually put the pass at risk

Nothing about the chess logic put the outcome at risk — the risk was entirely pacing. The agent used the unrecorded score endpoint (correctly, as the README instructs: "CI without pushing... Same pipeline, not recorded") for iteration, but let an entire turn and 79% of the wall-clock budget go by before making its first tracked push. Because a passing entry only exists once it is pushed to the task branch, everything discovered in that first turn was, from the benchmark's point of view, worth nothing until turn 2. The run's own metrics show one aborted request near the very end of the budget; if that abort — or any other disruption — had instead hit during the long unbanked first turn, or if the run's time limit had been a few hundred seconds shorter, the agent would have finished with a demonstrably working ~1000-rated policy and a score.log with zero entries. The recovery after the actual abort was handled well (it cross-checked its own sweep results rather than trusting a stale file), but that same care was not applied earlier to the much larger risk of never pushing anything.
