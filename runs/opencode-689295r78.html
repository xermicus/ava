Task and outcome

chess-vm: write bot.cvm, a move-scoring policy in the CVM assembly language, rated by playing 20 games against each of 27 built-in opponents. Both pushes the agent made passed. Entry of record: rating 1069 (field 0-1201), up from a starting sanity check of 316.

What the agent did, in order

  1. Read README.md and task.md, then immediately tried a trivial baseline via the free, unrecorded dry-run endpoint: tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080 → "rating": 316.27.... This confirms the agent understood from the start that scoring is free and only a git push origin task is recorded, and it used the free path to iterate.
  2. Wrote a hand-tuned linear feature policy (v1) combining MATERIAL, MOBILITY, OPPMOB, SEE, EXPOSED, MATEIN1, GIVESCHECK, ISCASTLE, ISPROMO, CENTER, HANGS, SAFE, KINGDIST with hand-picked weights, dry-ran it (942), and banked it at t=797s (~22% of the 3600s budget) with git commit -m "v1: weighted feature sum policy" && git push origin task. This immediately secured a passing floor early.
  3. Spent essentially the entire rest of the main turn (from ~t=800s to ~t=3480s, when the turn was cut off by the clock) building its own tooling rather than hand-editing further:
    • A full from-scratch Python chess engine (board.py, chess.py: move generation, legality, castling, en passant) to simulate games offline.
    • A CVM-to-Python translator/evaluator (build.py, cvm.py, score.py) so it could evaluate a candidate weight vector without invoking the real scorer.
    • Hill-climbing search scripts (hill.py, then hill2.py after finding a threading bug) that searched over weight vectors using this local approximation, since the real round-robin verifier takes too long to use as the search objective.
  4. Around t=3058s, it dry-ran a new v2 policy — piece-square tables plus material/SEE/mobility/king-distance/etc. — via the same free score:8080 endpoint and got the same rating it eventually banked: "rating": 1069.106.... It confirmed this repeatedly (full tree, bot.cvm alone, bot.cvm + README) with identical results.
  5. Instead of committing this immediately, it kept hill-climbing for roughly another 500 seconds, chasing further gains. Its own transcript shows this searching plateaued below what it had already found: "All give 1069 — the earlier mismatch was a threading race on shared temp dir." and later "base weights give 966, best 1069... The real win is a local [full search]". None of this extra search beat the 1069 already in hand.
  6. Turn 1 was killed by the run clock mid-experiment. monitor.json records {"elapsed_seconds":3480,"limit_seconds":3600,"turn":2,"last_call":true} — the harness started the last-call turn at 3480s. On resuming, the agent noted: "No log survived the interruption. The current bot (1069) is my best verified. Committing and pushing it now."
  7. It re-verified the workspace bot.cvm one more time (git diff --stat + dry run, still 1069), then committed ("v2: weighted policy with PST, exchange, mobility, king-distance") and pushed. The graded push landed at t=3550s, about 50 seconds before the 3600s budget expired, and passed with rating 1069 — the entry of record.

Why it passed

  • The agent used the unrecorded score:8080 endpoint exactly as the README hinted, so every push it actually made to task had already been dry-run verified with an identical pipeline; there is no daylight between what it tested and what it graded on.
  • It banked a working, decent baseline (941) very early (22% into the budget), which meant the run had a passing entry of record long before the improved version existed. If nothing else had gone through, the run still passed.
  • The last-call mechanism did its job: even though turn 1 ended abruptly mid-search, the harness resumed the session, the agent recognized its working tree already held the best-verified policy, and pushed it with time to spare inside the 120-second last-call window.

The agent's own mistake

The improved policy (1069) was fully verified via dry run at t≈3058s, with roughly 9 minutes of the main turn still remaining. The agent did not commit or push it then. Instead it spent that remaining time chasing further hill-climbing improvements that, by its own transcript, never beat 966-1069 and mostly underperformed the version already sitting in the workspace. That decision left the improved, already-validated entry unrecorded right up until the run's clock killed the turn — it was only banked because the last call fired and worked cleanly. Had the interruption instead corrupted the workspace, hit a SIGXFSZ/tmpfs cap, or had the last-call push taken longer than its 120-second allowance, the run would have ended with the weaker 941-rated v1 as the entry of record instead of 1069. Verification discipline was strong (dry run before every push); banking discipline was not — the agent treated "verified" and "safely recorded" as the same thing when only a push makes it durable.

The handful of 4xx/499 lines in proxy.access.log are the agent probing GET / and /help on the score endpoint (405, expected — it only accepts POST) and two of its own dry-run POSTs being cut off by its own bash timeouts/turn boundary, not proxy or scorer failures.
