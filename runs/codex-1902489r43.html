Task and approach

The task (chess-vm) asks for bot.cvm, a move-scoring policy in a small register machine (CVM) with no writable memory, no stack and no lookahead: for each legal move the engine runs the program once and plays whichever move scores highest. The starting file scored every move identically (a random mover). The agent's plan, stated up front (item_3: "mate detection, exchange safety, opponent mobility, development, promotions, castling, and king-move penalties"), was executed almost exactly as described.

First working version and early fixes

The first patch (item_6) already combined MATEIN1, SEE, OPPMOB, MOBILITY, EXPOSED, GIVESCHECK, ISCASTLE, ISPROMO, CENTER, pawn-rank scaling, a repeated-move penalty (MOVECOUNT) and a flat king-move penalty. It failed the assembler three times in a row on strict syntax: div r4, r4, 5 needed both operands as registers (bot.cvm line 18: '5' is not a register), neg r4 needed an explicit destination and source ('neg' takes 2 operands, got 1), and sub r12, r10, 1 again needed a register operand. Each fix was verified with the unrecorded CI call before moving on, and the fourth attempt assembled and returned the first real rating: 890 (item_25/item_26). This was pushed as the first recorded, passing entry at 120s.

Hill-climbing loop (890 → 1069)

From there the agent ran a disciplined single-variable sweep, always testing unrecorded first and only committing+pushing the improvement over the last pushed baseline:

  • Adding a flat material term and enemy-king-distance term regressed to 822 (item_19/item_20) and was reverted.

The saturation phase and one real bug caught pre-push

A second harness turn (item 250 onward) restated the current 1069 baseline and continued testing: material terms, ISCAPTURE bonuses, knight-specific bonuses, SAFE-gated minor-piece bonuses, and a piece-square-style .data lookup table indexed by destination file. Most of these tested as exactly 1069 unchanged — several turned out to be dead code from label bugs the agent introduced and then fixed without effect (duplicate not_pawn: / knight_done: labels caused wrong jumps at items 267-276; an inverted SUB r15, r10, r14 vs r14, r10 sign bug at items 289-291). The most serious near-miss was the file-indexed .data table: after fixing an addressing bug, it briefly caused bot.cvm line 34: LD read data address 18, outside 0..16 and failed 19774 of its decisions with a fault before the fallback of "play the first legal move" kicked in (item 343). Because this was run through the unrecorded score:8080 endpoint rather than pushed, the failure never touched the graded branch; the agent fixed the table size, then found the whole feature was a wash (best case 1069, same as CENTER) and reverted to the simpler CENTER-based term (item 347).

Why 1069 held as the ceiling

The scoring rubric plays the submission against 27 opponents from a random mover up to a 4-ply search. The score.error.log's win/draw/loss table for the final 1069 policy shows it sweeping the weak and mid-tier opponents (20-0-0 vs cccp, alphabetical, opposite_color, equalizer, composite) but losing badly to the deep search-based opponents: 0 wins/1 draw/19 losses vs steady, 3/2/15 vs sensei, 9/10/1 vs positional. A one-ply, no-lookahead policy structurally cannot out-calculate multi-ply search opponents; the agent's own conclusion (item 387: "No tested feature improved beyond 1069; the only useful result is a neutral instruction cleanup") matches this — it had exhausted the space of cheap static heuristics reachable in 256 instructions without lookahead.
