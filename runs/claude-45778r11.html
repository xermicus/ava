Task and setup

chess-vm asks for bot.cvm, a single-ply move-scoring policy in a small register CVM assembly language (16 registers, read-only data, no stack, no .search, 256 instructions / 1024 data words / 20M cycles). The verifier plays the submission 20 games against each of 27 built-in opponents and converts the result into an ELO-style rating on a 0-1201 scale; a push only fails if the program faults or exhausts its cycle budget on some decision. Every push in this run passed — the agent never submitted a broken program to the verifier.

What the agent did

It first probed the baseline: a trivial 3-instruction bot rated 316. Recognizing that hand-writing and tuning CVM assembly by hand would be slow, it wrote gen.py, a Python generator that emits the assembly from a set of feature flags and weights (env vars), so it could regenerate and re-score a variant in one command:

"Let me build a generator script so I can iterate on weights/tables easily."

The first generated version (phase-blended midgame/endgame piece-square tables) already reached 828. From there the agent ran a long sequence of feature experiments against the live score endpoint, keeping what measurably helped and discarding what did not:

  • Mobility differential (own moves minus opponent moves, asymmetric weights 4/3) and SEE-weighted capture scoring were the two biggest wins, taking the bot from ~828 to 959.5.
  • It added king-safety (ring-of-8 attacker/defender delta table), reaching 946-965 depending on companion weights.
  • Move-count-based development discipline (MOVECOUNT penalty, -30) added another few points (963.7 -> 965.1).
  • Isolated-pawn penalty (-20) added ~3 points once a real bug in the pawn-structure code was fixed (see below), reaching 967.9, then a re-tuned check-avoidance weight pushed it to 972.2.
  • A late discovery that the phase-cap constant had a sharp, narrow optimum near 5880 (978.0 -> 979.4 -> 982.3) and a final castle-bonus retune (150-170, settling on 160) reached the final 983.8, reported by the verifier as rating 984.

Ideas it tried and correctly abandoned after measurement: passed-pawn bonus (consistently negative, -1.4 to -98 depending on scale), bishop pair, PeSTO piece-square tables (worse than the CPW tables already in use because they fight the mobility term), doubled-pawn penalty, center-occupation bonus, wider (2-ring) king safety, shield bonus, and enemy-king-distance attack bonus. In each case it changed one variable, re-scored, and reverted rather than assuming the idea should work.

Self-caught bugs

The agent introduced and fixed several real bugs in its own generated assembly, all caught through score regressions or a hand-rolled CVM simulator rather than blind trial and error:

  • A register-allocation bug clobbering r8 (the phase divisor) with piece kinds mid-scan, which silently produced a lower rating (805) until traced.
  • An off-by-one in the king-safety delta-table read (loop ran 9 times over an 8-entry table), diagnosed from a fault message citing an out-of-range data address.
  • A passed-pawn implementation that double-incremented a loop counter on a specific branch, which did not fault but corrupted move selection and dropped the rating to a catastrophic 306; the agent traced this with line-by-line control-flow reasoning and a purpose-built Python CVM simulator with edge-case boards (king in corner, empty board) before re-testing.

It also noticed identical ratings across several weight variants and correctly diagnosed this as the sweep being quantized by move-choice ties rather than assuming its harness was broken — evidence it was reading its own experiments critically rather than accepting any number the scorer returned.

The subagent detour

At 09:59 the agent launched a background Agent (a32dd3451bb70365c) to sweep a grid of weight combinations in an isolated copy of the workspace while it kept working by hand. It later lost track of the subagent's status (its own note reads, in part, "the agent seems to have finished but I didn't see a notification"), asked it directly via SendMessage, and eventually TaskStop'd it near the very end after concluding its own manual, more targeted sweep had already covered the same parameter space. This did not cost the run anything — the manual sweep was thorough — but the subagent added coordination overhead (ListAgents, SendMessage, waiting, TaskStop) without producing an improvement the agent didn't already find itself.
