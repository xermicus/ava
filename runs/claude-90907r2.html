What happened

The task ([games/r2wars](../ava-book/games.md)) asks for warrior.x86-32.asm: a Core War warrior for r2wars' x86-32 ESIL emulator, ranked entirely by fights rather than by passing alone ("Passing is all there is to rank on its own, the fights are what tells warriors apart.").

Turn 1 (780s): failed push, no file

The agent's first git push origin task was attempted before any warrior.x86-32.asm existed in the workspace -- it was still experimenting in a scratch directory /tmp/war. The verifier correctly rejected it:

remote: pipeline: {"seconds": 780, "passed": false, "reason": "no warrior.x86-32.asm in the submission"}

Turn 2 (802s): a placeholder pass

Twenty-two seconds later the agent wrote the minimal possible warrior and pushed it:

printf 'jmp $\n' > warrior.x86-32.asm && rasm2 -a x86 -b 32 -f warrior.x86-32.asm && git add -A && git commit -q -m "imp warrior" && git push origin task

This is the classic Core War "imp": an infinite self-loop that never reads, writes, or attacks anything. It assembled to 2 bytes and passed:

[2026-09-16T17:02:33Z INFO  ava_game::r2wars] warrior.x86-32.asm assembles to 2 bytes
[2026-09-16T17:02:33Z INFO  ava_scorer::score] the r2wars-x86-32 submission of turn 0 passed

This is the only entry ever recorded (entries/802/warrior.x86-32.asm contains just jmp $), and the only file ever pushed for the rest of the run.

The rest of the run: pure research, no second push

From roughly minute 15 to minute 85 of the 90-minute budget, the agent ran an extended, genuinely competent reverse-engineering campaign against the ESIL emulator, entirely inside /tmp/war, never touching the pushed branch again:

  • It built a black-box test harness (harness.py, a tourney() wrapper around r2wars --fight) and ran the placeholder against the bundled jordi example 20 times, finding the imp actually wins most fights by default because jordi self-destructs sweeping out of bounds ("Executed invalid instruction 0x00000400" 12/20 times) -- a real and useful discovery about this ruleset, but one that only explains why the placeholder isn't a total write-off, not a plan to improve on it.
  • It single-stepped ESIL state (r2 malloc://1024 with aei/aeim/wx/aer/aes) to nail down arena bounds ([0, 0x400)), self-write persistence, and the surprising survival of self-overwriting warriors.
  • The decisive technical finding: "rep stosb costs a constant 1 cycle regardless of ecx -- that's the key exploit", meaning a warrior can wipe the entire 1 KiB arena in about the same time as one ordinary instruction, which should dominate against any warrior that writes byte-by-byte or in a loop.
  • It then designed and validated (in ESIL, not yet against real opponents) a self-relocating "bomber" that copies itself past the point its own wipe would otherwise erase it, confirming with px/aer dumps that the copy landed correctly and left address 0 intact.

At no point during those ~70 minutes did the agent write this design out as warrior.x86-32.asm, assemble it for a real submission, run it through its own tourney() harness against the example opponents, or push it. The last tool call of the run (18:20:25Z) is exactly the verification step confirming the self-relocation copy worked -- one step short of turning it into a submission.

The backend cut the run short right after

Immediately after that last tool result, the backend returned a 500:

{"type":"system","subtype":"api_retry","attempt":1,"max_retries":10,"retry_delay_ms":526,"error_status":500,"error":"server_error", ...}

matching a 500 POST in proxy.access.log at 18:20:35Z. After the retry, the agent log fills with roughly 5,000 consecutive thinking_tokens heartbeat events carrying no assistant text or tool_use -- effectively silence -- until a fresh session init appears near the very end of the log, which immediately hits:

[claude-code:unrecognized_model] {"model":"parity/deepseek-v4.1-flash","query_source":"sdk"}

The harness could not resolve the model route for what looks like the run's last-call turn, so nothing further was produced. monitor.json confirms the run ended in "last_call":true at elapsed_seconds:5341 against a limit_seconds:5400, with "silent_seconds":58 -- consistent with a stalled final turn rather than a deliberate stop.

Why it ended where it did

Two things had to both go wrong for the run to end with only the placeholder banked:

  1. Agent pacing. The agent never treated "push something better than the placeholder" as an active goal to interleave with research; it ran a single long unbroken investigation and only reached a submittable design in the closing minutes, with no earlier checkpoint (e.g. the plain rep stosb sweeper, which it had already benchmarked well before the bomber) pushed as a fallback better than jmp $.
  2. A backend failure at the worst possible moment. The 500 error and the subsequent failed session resume (unrecognized_model) landed right as the agent would have turned its validated design into a push, and the harness's recovery path did not get the agent talking again before the container's time ran out.

Because r2wars ranks entries only by their fights, not by the CI pass, the entry of record -- a two-byte infinite loop that never attacks -- will do essentially nothing against a competent opponent (best case a draw by timeout, or a win only if the opponent self-destructs) despite the run showing a clean passed: true.
