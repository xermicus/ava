What happened

The task is r2wars-x86-32: write warrior.x86-32.asm, an x86-32 Core War warrior for radare2's ESIL-based r2wars engine. Per the book, passing only requires the file to assemble with rasm2 to 1-512 bytes -- ranking/quality comes from fights the scorer runs separately and does not gate pass/fail.

Exploration and engine reverse-engineering (commands #1-27, elapsed 0-~4900s)

The agent read the r2wars README and bundled examples (jordi, pancake), then built a hand-rolled ESIL test harness around r2 -q -c '...aes...' to single-step candidate instruction encodings and observe register/memory/PC state. This is solid, careful work: it empirically confirmed which opcodes trap (0xCC int3, 0xF4 hlt, 0x0F 0x0B ud2 all trap; 00 00 does not), validated rep stosd and pusha semantics, and worked out label arithmetic for building position-independent code via call getpc / pop ebx / sub ebx, 5.

Not satisfied with black-box testing, the agent found and CIL-disassembled the closed-source r2wars.dll (a .NET binary) with radare2's -a cil mode, tracing methods like iniciaJugadores/resetTablero/iniciaCombate to understand load-position selection and whether warriors could overlap. This is an impressive but very expensive detour -- roughly commands #44-59, a large fraction of the run -- for a game whose pass bar is "assembles to a legal size."

Building the warrior (v1 -> v2 -> v5 -> v6)

  • v1: self-locates, fills memory before/after its own code with 0xCCCCCCCC via a mov+loop.
  • v2/v6: same self-location, but fills using pusha (writes 32 bytes at once) for speed, after loading all eight registers with the bomb pattern -- a much stronger design since r2wars scores fights by cycles/instructions executed.
  • v5: a passive-testing variant with a fixed idle loop, used to sanity-check that a fill warrior actually beats a harmless opponent.

The agent tested v2 against jordi and against a no-op loop (30-fight batches) and observed it beat jordi and the loop but raced pancake, then kept refining toward v6 (pusha-based, all 8 registers loaded with the bomb pattern). This is a reasonable, real Core War strategy (a "bomber"/carpet-fill warrior), well suited to a game where you don't know where the opponent loads.

The scoring channel confusion (the core mistake)

Two ways exist to check a submission: tar | curl directly to score:8080 (an informal probe hitting the same verify logic, per score.error.log), and git push origin task (the actual graded channel recorded in run.json's attempts). The agent's early v1 warrior passed via the curl probe at elapsed ~492s (score.error.log: "warrior.x86-32.asm assembles to 47 bytes ... passed" at 11:00:11, only ~8 minutes into a 90-minute run) -- but this was never pushed through git, so it did not count as an official attempt. run.json's attempts array only starts at elapsed 5037s, meaning the agent's first graded push happened with only 363 of 5400 seconds (6.7%) left.

Worse, once actually pushing near the end, the agent misread the informational seconds field the score endpoint echoes back (e.g. {"seconds": 5291, "passed": true}) as a warrior-quality metric. Its own words: "The metric is deterministic and higher is better (v6=5213, passive=5167, ud2=5143). Let me build a scoring harness to optimize against it." It then push-tested a bare ud2 (instant self-crash) and a nop;jmp idle no-op warrior to the real scored branch purely to compare their returned seconds values, spending several of its last graded pushes (entries at 5143, 5167, 5278 are the degenerate ud2/idle files) chasing a number that is, per the book, just the run's elapsed-time clock, not a fitness score. It caught the error only after noticing v1/v2/v5 all "coincidentally" returned the same value ("suspicious"), and with the clock nearly out, wrote: "Time is up. Let me restore the strongest warrior (v6) and push immediately," landing the final, correct push at elapsed 5303s -- 97 seconds before the 5400s limit.

Why it passed anyway

Because the game's pass bar is trivial (valid assembly, 1-512 bytes) and the last push happened to be v6 (the real warrior, confirmed by entries/5303/warrior.x86-32.asm matching the call getpc/pusha pattern), the run ended with a good, competitive submission banked. But this was closer to a near-miss than a clean execution: 93% of the budget elapsed before any graded push existed at all, and part of the final 5 minutes was actively spent overwriting the graded branch with throwaway warriors while pursuing a misunderstood signal. Had the last recovery push been delayed by even a couple of minutes, or had the aborted LLM request at 12:19:59 (proxy 499, recovered on retry) not recovered cleanly, the run could easily have ended with either no passing entry or a degenerate one (ud2/idle loop) left as the final scored state.

Bottom line

The agent's technical work -- ESIL semantics discovery, CIL reverse engineering, and the final pusha-bomber design -- was strong and shows real understanding of the game. The process failure was entirely about the scoring/banking loop: it treated the whole 90-minute budget as free exploration time instead of banking a known-good pass immediately and improving from there, and it fabricated meaning from a log field it never checked against documentation, nearly spending its margin on that fabrication.
