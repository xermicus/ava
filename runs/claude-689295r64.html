Task

r2wars-x86-32: submit warrior.x86-32.asm, a Core War warrior for radare2's r2wars engine on x86-32, judged first by whether it assembles to 1-512 bytes (the only thing a single push can be graded on) and later by fights against other seats' entries, which the agent cannot observe directly.

What the agent did

The agent had no access to the r2wars engine's source (a compiled .NET DLL, r2wars.dll); it spent a long early stretch (tool calls around lines 316-2445 of agent.log) trying to extract cycle-cost and mechanics information via strings on the DLL and searching for a decompiler (ilspycmd, monodis, ildasm, nuget packages) — all absent from the sandbox. This was ultimately a dead end; the agent fell back to black-box empirical testing.

It built a fight.sh harness to run r2wars --fight A B repeatedly and tally results, initially misparsing the winner line (.asm extension is stripped from the reported winner) and fixing the bug once noticed:

"The winner line drops the .asm extension. Let me fix the comparison."

With a working harness, it read the bundled example warriors (jordi, pancake) and wrote a classic self-replicating 'imp': a call/pop-based position-independent copier that duplicates its own 24-byte body 24 bytes ahead and jumps there. It tested this against the examples, found it strong, and pushed it at 829 seconds — banking a guaranteed pass just 14 minutes into a 5400-second run:

; 24-byte self-replicating imp
start:
    call getpc
getpc:
    pop esi
    lea edi, [esi+19]
    mov ecx, 6
    sub esi, 5
    rep movsd
    jmp edi

With a safe entry in hand, the agent spent the rest of the run — well over an hour — trying to find a stronger warrior, since points in r2wars come only from fights, not from the push itself. It:

  • Built a diverse opponent suite of its own (scanner, several bomber variants, a self-healing vampire, and imps of varying stride) to stand in for the hidden field.
  • Discovered that a non-wrapping imp eventually runs off the 1 KiB arena edge and dies, while masking the jump target (and edi, 0x3ff) lets an imp wrap and survive indefinitely — but also found that two identical wrapping imps draw forever against each other, and that 'bomber' opponents can still corrupt a wrapping imp's code and force a draw or loss.
  • Wrote a parameterized candidate generator (gen_imp) to sweep stride/copy-count/wrap combinations and ran multiple rounds of round-robin evaluation (eval.sh, rr.sh) with 10-40 fights per pairing to smooth out noise from randomized start positions.
  • Hit a self-inflicted snag: the generator had an off-by-stride bug, so a candidate it believed was an 8-byte-stride imp was actually built with the wrong offset, producing results that flatly contradicted earlier findings ('imp8w beat jordi 10/10, but i8n2w loses 0/10... Let me compare them'). It traced this to the bug, fixed the generator, and re-ran the sweep.
  • Converged on a 24-byte-stride, 6-dword-copy wrapping imp (s24n6w) as the most robust design across the suite, verified it still beat the two bundled examples, and pushed it at 5344 seconds — 56 seconds before the 5400-second limit, inside the run's last-call phase (monitor.json: elapsed_seconds:5341, limit_seconds:5400, last_call:true).

Both pushes passed (score.log: {"seconds": 829, "passed": true}, {"seconds": 5344, "passed": true}). score.error.log only shows one 'passed' log line, at 17:15:27, which lines up with neither push's wall-clock time exactly — a minor gap in the sidecar log rather than a sign either push failed; run.json and score.log agree on two passing attempts and are the authoritative record.

Why it passed

The task's only hard requirement for a push to pass is assembling within 1-512 bytes; both the 24-byte and 55-byte warriors easily satisfy that. The agent never risked a 'never wrote' or 'unbanked' outcome because it deliberately pushed a known-good design early, before spending its exploration budget. The final push, despite landing with only 56 seconds of margin, still made the deadline.

What could have gone better

The multi-hundred-tool-call detour trying to find a DLL decompiler was pure loss — nothing in the sandbox could produce one, and the agent had no way to confirm that before trying. A faster pivot to black-box fighting (which is what eventually worked, and which the task description itself hints at: 'the reverse engineering the game asks for') would have freed up time for a larger round-robin sweep. Separately, the candidate-generator stride bug shows the agent's own tooling introduced noise into its empirical process; it caught and fixed it, but only after drawing an incorrect conclusion from it. Finally, submitting the improved design with under a minute of margin left in the run was risky style even though it worked — a slower verifier or one more debugging round would have meant losing the improvement and falling back to the weaker 829s entry.
