What happened

The task was chess-vm: write bot.cvm, a branch-free move-scoring policy in the CVM assembly language, and push it to the task branch. Every push is verified immediately against a field of 27 opponents and rated 0-1201; the entry with the highest rating stands.

Turn by turn

The agent (lisa, GLM-5.3 via Claude Code harness, high thinking effort) read the task, inspected the workspace, and found dev/lint.py and the CVM spec already present. It wrote a first policy combining static exchange evaluation (SEE), mate-in-1, promotion/castling/check bonuses, centralisation and pawn-advancement piece-square weights, and a mobility differential - all "straight-line" with no branches, deliberately avoiding fault risk (per its own comment: "No branches -> no fault risk").

It tested this via tar -c --exclude=.git . | curl ... http://score:8080 — the game's unrecorded score-check endpoint, distinct from a real push to the git host — first getting a rating of only 316 on a 3-instruction stub, then iterating up. Once the fuller v1 policy scored well in local testing it committed and pushed to task at elapsed 2140s, landing rating 934.7 (score.log line 1, entries/2140/bot.cvm).

It then added an EXPOSED safety term (penalizing leaving the most valuable piece en prise) as v2b, tested it via score:8080, and pushed it at 2209s for rating 940.1 (entries/2209/bot.cvm, commit message "v2b: add EXPOSED -3 safety term (rating 940)").

From there the agent ran a wider A/B sweep (v2a-v2d, v3, v4, v5, v6, v7), generated with a dev/gen.py/dev/mkbot.py template pipeline, testing doubled-pawn penalties, phase-aware king handling, and heavier mobility/castle/check weights - all of which scored worse (879-920) and were discarded. The ambitious variant, v7, added a full 64-square piece-square-table scan (PIECEAT/CENTER-style loop over all squares, summing per-piece-kind PST values with a king table blended by game phase). Getting v7 to actually run took two rounds of bugfixing purely from score:8080 test failures logged in score.error.log:

  • bot.cvm line 58: '6' is not a register, the registers are r0 through r15 (12:28:20) — a generator template bug (dev/gen.py had wrong placeholder mapping between %ROOK_ROWS% and %BISHOP_ROWS%, fixed in-band).
  • bot.cvm line 75: 'NEG' takes 2 operands, got 1 (12:40:13) — NEG r8 / NEG r4 needed a second operand; fixed with a sed patch and a matching fix to the generator so future runs wouldn't regenerate the bug.

Only after v7 finally passed the unrecorded score check at rating 1020 (12:49:29) did the agent commit and push it for real, landing at elapsed 3504s - inside the harness's last_call window (monitor.json: elapsed_seconds:3480, turn:2, last_call:true) and about 96 seconds before the 3600-second limit. The agent's own closing thought captured the risk it had taken: "The gamble paid off — v7 passed at 1020, well above v2b's 940. Time is up per the instruction, so I'll stop here and report."

Why it passed

All three official pushes passed verification cleanly (bot.cvm has N instructions and M data words, playing it against the field / ... passed in score.error.log), because the agent never pushed an untested version to the real task branch - every push had already cleared the unrecorded score:8080 endpoint, including the two intermediate assembly errors that were caught and fixed before they could cost an official attempt. This discipline is what let the agent safely gamble on the higher-risk v7 rewrite this late: a broken push would merely have left the 940-rated v2b as the best entry, not failed the run outright, because AvA keeps the best-rated passing entry regardless of later failed pushes.

What could have gone better

The agent spent roughly the first 37 minutes of a 60-minute budget reaching only a modest, mostly hand-tuned evaluator (935 -> 940), then attempted the substantially harder PST-scan rewrite in the last 23 minutes, which needed multiple debug cycles purely because of avoidable assembly mistakes (wrong register operand, wrong instruction arity) in generated code that wasn't checked with the dev/lint.py linter before the score-test round that surfaced them. Running the linter consistently before every score:8080 test, or starting the ambitious rewrite earlier, would have given more margin than the ~96 seconds separating this run's actual outcome (1020) from a run that ran out of clock with only 940 banked.
