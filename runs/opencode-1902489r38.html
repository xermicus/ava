Task

chess-vm asks for bot.cvm, a move-scoring policy (not a search) for a register VM, limited to 256 instructions, 1024 data words, and 20M cycles per decision. Every push is rated by playing 20 games against each of 27 built-in opponents (from a random mover to a 4-ply searcher) and converting the results into a rating.

What the agent did

It read README.md and task.md first, noted the workflow hint that pushes to task are graded and recorded but tar -c --exclude=.git . | curl ... http://score:8080 runs the same pipeline without recording it, and used that distinction as its whole development loop:

  1. Probed the CI with the starter trivial bot (bot.cvm has rating 316) via the score endpoint to learn the feedback format (agent.log:217).
  2. Wrote v1 (material + SEE-based exchange safety + mate/mobility, 95 instructions), self-tested via score (rating 913), then committed and pushed to task (git push origin task, recorded seconds=1683, rating 913.38) — this matches score.log line 1 exactly.
  3. Repeated this test-then-push cycle for v2 through v10, each time self-testing via score:8080 first and only pushing to task when the result held or improved: 947 (v2), 1109 (v5, after fixing a bad register-immediate bug), 1147 (v6), 1158, 1160, and finally 1174 (v10).
  4. Along the way it hit several self-inflicted failures, all caught by the same self-test loop before or (in a few cases) after they reached the graded branch:
    • bot.cvm line 144: '0' is not a register, the registers are r0 through r15 — a JGT r12, 0, oursq used an immediate where a register was required; the agent diagnosed and fixed this in the next message (agent.log:502).
    • Instruction-count overruns twice: the code section is 260 instructions, the limit is 256 and later 273 instructions — the agent had built an instruction counter (grep -vE '^\s*(;|$)' bot.cvm | grep -cv ...) but did not always run it before testing, so it discovered the overrun only from the CI's rejection.
    • A .word directive placed outside a .data block (line 313).
    • A version that assembled cleanly but faulted at runtime: PIECEAT was given square 64, outside 0..64, which fired on 17,632 of the decisions during that submission's 20x27 games and dragged its rating down to 469 (score.error.log, 11:41:31) — the engine falls back to playing the first legal move on a fault, so this version was effectively broken. Because this was caught via the unrecorded score endpoint, not a push to task, it never reached score.log/run.json's attempts at all (the verifier logs it as "failed" immediately after reporting the fault) — it cost wall-clock and tokens but not recorded rating.
  5. After the instruction budget got tight (250/256), the agent spent its final ~15 minutes on small parameter sweeps (trade bonus, king-safety weight, enemy-king-attack scaling) around the v9/v10 plateau, mostly finding the rating insensitive to these tweaks ('Same rating — these terms rarely bind', 'All variants tie at 1174 — this term doesn't bind in the fixed games'), before settling on v10 (250 instructions, rating 1174).
  6. Committed v10, pushed to task (recorded at seconds=3144, rating 1173.89 — matches run.json's final attempt and score.log's last line), then immediately git tag release && git push origin release, and the scorer responded 'release received, the run ends'.

Why the pushes that failed, failed

All 11 failed verifications in score.error.log are the agent's own authoring mistakes against the CVM assembler/VM's stated constraints (register syntax, the 256-instruction cap, .data/.word ordering, and a square-index bounds check), not anything wrong with the harness or backend. None of them reached the recorded task branch as a regression — the git-receive-pack log (proxy.access.log) shows 10 real pushes, and the 8 lines in score.log/run.json's attempts are exactly those pushes that both succeeded and improved (or matched) the rating, confirming the agent's push discipline: it only pushed once its local self-test via score:8080 had already passed with an acceptable rating, so a failing/regressing candidate was iterated on further before it was ever committed to task.

Bottom line

This is a case where a noisy, error-prone editing process (four distinct classes of syntax/fault bugs surfaced over the run) did not damage the graded outcome because the agent consistently gated every push behind the unrecorded self-test endpoint. The recorded rating trajectory is monotonic and the final push happened with time to spare, tagging release deliberately rather than being cut off by the clock.
