Chess-VM run analysis

Task and approach

The task asked for bot.cvm, a move-scoring policy in the CVM assembly language for the chess-vm game: a single-shot evaluation run once per legal move, no search, no lookahead, 256 instructions / 1024 data words / 20M cycles per decision. The starting bot.cvm scored every move equally (a random mover). The agent read SPEC.md and task.md, noted the CI endpoint hint (tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080, unrecorded), and adopted a tight loop: write or tweak one evaluation term, run it through the unrecorded endpoint, keep it only if the rating rose, then commit and push (which is recorded) once a gain was confirmed.

Turn-by-turn (by push)

  • 200s -- rating 909: first working evaluation (material + basic terms) after fixing an early bug (DIV needs a register divisor, not an immediate).
  • 716s -- rating 948: after many single-term experiments (attack-proximity, pawn-advance, minor-piece development, castling bonus, exposure penalty tuning, center weight), landed on a base with mobility, castling, and a half-strength exposure penalty. Several ideas were tried and reverted along the way (ENEMYKINGDIST hurt, SAFE reward hurt, full exposure penalty was worse than half).
  • 915s -- rating 1049: a king-move penalty (-140) plus an early-queen-development penalty (-80 for early queen moves) produced the run's single biggest jump, from 982 to 1049.
  • 1066s -- rating 1052: gated the queen penalty to non-capturing moves only; gating the king penalty the same way hurt, so only the queen change was kept.
  • 1498s -- rating 1057: check bonus retuned to 20.
  • 1754s -- rating 1069: rewarded first-time minor-piece development (+60 after tuning from +20).
  • 2045s -- rating 1076: retuned the queen penalty magnitude to -60.
  • 2413s -- rating 1076: reconfirmed the same 1076 build after a PLY window micro-tune (12 vs 10 vs 16) settled back on the original value.

From push 7 onward (roughly 2045s to 2644s) essentially every further idea tried -- endgame king-activity reduction, endgame pawn-advance weight, a piece-square-style rank curve, opponent-mobility reweighting, a promotion bonus, a rook-on-7th/rook-activation reward, a "big win" SEE bonus, a flat capture bonus, exposure-penalty gating to non-captures, minor-piece re-move penalty -- either was neutral or made the rating worse (some drops were large, e.g. central-development stacking cratered it to 935, exposure gating to 913). The agent correctly identified and reverted every regression, so the committed state never got worse, but no further gain was found. It then confirmed the working tree matched the last committed 1076 build (git log, git status, wc -l bot.cvm) and tagged release, ending the run at ~2644s of the 3600s budget.

Why it passed

Every push in score.log passed; the game only fails a push when the program faults or exhausts its cycle budget, which never happened here. The agent's discipline -- test on the unrecorded endpoint first, only push after a confirmed win, revert cleanly on a regression -- meant the recorded (pushed) history is monotonically non-decreasing in rating (909 -> 948 -> 1049 -> 1052 -> 1057 -> 1069 -> 1076 -> 1076), and the final push was a genuine best, not a leftover experimental state.

What could have gone further

The last ~600s of tuning (pushes 7-8 and beyond) show diminishing returns: nearly every remaining idea in the same family of hand-tuned linear terms failed to beat 1076. The agent judged this a plateau and stopped with time left on the clock rather than trying a structurally different mechanism, such as a real piece-square table via .data (it did attempt this once, "Rank curve worse (1034); reverting to linear," but did not pursue a broader data-table redesign). That is a reasonable judgment call given the string of failures, not a mistake, but it is the one place a different agent might have found more headroom in the unused budget.
