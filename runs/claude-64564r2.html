What happened

The agent read README.md and the chess-vm SPEC.md, then set up a submit.sh helper that posts a tar of the workspace to the unrecorded http://score:8080 CI endpoint (the "CI without pushing" path the README calls out), which it used for essentially every iteration instead of the real git branch.

Minute 0-2: baseline test of the starter bot.cvm scored rating 316 (random-mover level).

Minute ~6 (11:11:53Z): a hand-written evaluator (MATERIAL - GAIN combined with SEE) scored 892.6 on first try — a strong result reached very early. Immediately after, at 11:12:18Z, a slightly different variant dropped to 879.8 and the agent kept iterating around that number without noticing the regression from 892 to 879, and — critically — never pushed either of these bots to git.

Minutes ~7-38 (11:13-11:44Z): the agent built increasingly elaborate parallel-evaluation infrastructure (search.py, par.py, par2.py, up to 48-way parallel CI probes) to hill-climb weights, spending most of this window benchmarking the scorer's own throughput and content-caching behavior ("The server caches by content hash", "16 distinct evals: 121s wall → ~7.6s/eval throughput") rather than improving the bot. Several long sleep 100-115 polling loops were used to wait on backgrounded search jobs. Net progress in this window was flat to negative: rating stayed at 879.8 through 11:29:34Z, then a run of an unsupervised search script (screen1.py) produced a worse bot at 820.6 (11:45:16Z).

Minute ~44 (11:49:58Z): the agent finally diagnosed the root cause of the stall: "The base was wrong: subtracting GAIN from both MATERIAL and SEE double-penalizes captures. My earlier 893 bot effectively used mat_before + SEE."* This is the same bug that its own final push summary calls out: "MATERIAL already includes the captured piece, so naively combining MATERIAL − GAIN with SEE − GAIN double-penalises captures and lost ~330 rating."

Minutes ~48-58 (11:54-12:03Z): with the bug fixed, the agent switched to a full 64-square board scan using PIECEAT, accumulating material plus a piece-square table (with orientation handling via TORANK/TOSQ) for every piece, plus SEE, MOBILITY - OPPMOB, and MATEIN1. This reached rating 925.3 at 12:03:00Z.

Minute ~59 (12:04:37-12:05:08Z): the agent spot-checked one more orientation variant, confirmed both were equivalent (925 each), then ran git add -A bot.cvm && git commit ... && git push origin task. The push landed at 3552s of the 3600s budget and the CI reported it passed at entry offset 3561s ({"seconds": 3561, "passed": true, ..., "rating": 925.3029487410874}), 39 seconds before the hard cutoff. The subsequent last-call turn made one more identical push (entry offset 3588, same rating), which is the second line in score.log.

Why it passed, and how close it came to not passing

The final bot is a legitimate, reasonably sophisticated policy — full-board scan, PST, SEE, mobility and mate-in-1 detection — and it scored 925 against a field ranging 0-1201, well clear of the 316 random-mover floor. The bot.cvm files at both entries (entries/3561/bot.cvm, entries/3588/bot.cvm) are byte-identical, confirming the second push was just the last-call repeat of the same solution.

But the run's pacing was reckless: a working ~893-rated bot existed 6 minutes into a 60-minute budget and was never once pushed to the real branch. Instead the agent spent roughly half the run (11:13-11:44Z) on parallel-search tooling that made no net improvement over the already-buggy 879-rated baseline, and briefly regressed further to 820. Only after diagnosing its own double-counting bug at the 44-minute mark did it make real progress, and the winning bot was found with barely two minutes of budget left. The only git push of the entire run happened 48 seconds before the deadline. Had the final board-scan rewrite, the orientation-equivalence check, or the scoring round trip taken even a little longer, the run would have ended with zero banked entries despite multiple viable bots (892, then 925) having existed well before the deadline.

Attribution

No environment problems: metrics.failed_requests, truncated_requests, and aborted_requests are all 0, both git pushes and both score.log verdicts succeeded, and the harness ran a normal last call. The near-miss was entirely the agent's own risk management — good iteration and a genuine self-caught bug fix, undercut by never banking a safety-net entry until the very last possible moment.
