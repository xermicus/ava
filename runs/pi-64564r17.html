Chess-VM run analysis (deepseek-v4.1-flash / pi harness)

Task and outcome

The task asked for bot.cvm, a one-ply CVM move-scoring policy, graded by the rating it achieves over 20 games against each of 27 built-in opponents. The run passed with a single recorded attempt:

{"seconds": 3596, "passed": true, "reason": "bot.cvm has rating 1028, the field ranges from 0 to 1201", "rating": 1027.7607701742245}

That is the only line in score.log. Every other test the agent ran, over 150 of them, went through the unrecorded http://score:8080 endpoint and never touched the graded task branch.

What the agent built

Starting from the stub bot (ldi r0,0; score r0; halt, rating ~random), the agent iterated through:

  1. Hand-written linear terms tested one at a time against score:8080 via a try.sh wrapper: MATERIAL alone (544), then +SEE+MATEIN1+MOBILITY+EXPOSED combinations.
  2. Python tooling (gen.py, evalbot.py) plus automated search (search.py, randsearch.py, locsearch.py) doing greedy/coordinate-descent and random search over term weights {MATERIAL, SEE, MATEIN1, MOBILITY, OPPMOB, EXPOSED, GIVESCHECK, SAFE}, converging on a plateau of 989.63, repeated for roughly 90 evaluated weight sets: EVAL 989.6299 [["EXPOSED",-1],["GIVESCHECK",100],["MATEIN1",100000],["MATERIAL",1],["MOBILITY",1],["OPPMOB",-1],["SAFE",200],["SEE",2]]
  3. Piece-square tables, tried and discarded as worse (PSTd4.cvm: 936, PSTd8.cvm: 985).
  4. A new generator (gen2.py) adding a 64-square scan for the most valuable undefended piece left hanging (PIECEAT/ATTACKERS/DEFENDERS over every square), which pushed the rating from 989.6 to 1027.76 (U_d.cvm: 1027.7607701742245), the run's actual best design.
  5. A follow-up attempt to add a symmetric enemy-threat scan (E1.cvm, E2.cvm) failed to assemble ("bot.cvm line 58: label 'scan' is defined twice") around second 3235 and was abandoned rather than debugged, in favour of the already-known-good M_undef variant.

This is a coherent, competent tuning process for the game, and turned a random mover (rating 316) into a rating-1028 bot, comfortably mid-field of the 0-1201 range.

The decisive mistake: nothing was ever banked

The README given to the agent says explicitly: "Submit by committing the task results and pushing the task branch... Keep improving the solution and commit + push subsequent submissions after the first passing one." The agent never did this. It reached its final rating of 1027.76 by roughly second 2920 (elapsed), with about 680 seconds of ordinary budget and the entire last-call turn still ahead of it, and never once pushed to the task branch during that time. Every one of its 150+ real submissions went to the unrecorded score:8080 mirror, which leaves nothing on task and banks no entry at all.

This meant that going into the final seconds, the only thing standing between the run and a zero score was the agent successfully reconstructing the exact same bot one more time and pushing it correctly, with no safety margin.

That is exactly what nearly went wrong. The book documents that /tmp "is a small tmpfs of its own and no restart carries it over" (unlike /home/agent, which does survive the last-call restart). The agent's tooling — gen2.py, the search scripts, and all the intermediate variant files — lived in /tmp, not in the persisted home or the workspace. When the time-up prompt fired the last call and the sandbox restarted, /tmp and /tmp/v came back empty:

"ls: cannot access '/tmp/v/': No such file or directory
/tmp/:
=== workspace bot ===
..."

Worse, the file actually sitting in the workspace at that moment was a broken variant (E4, the failed enemy-threat scan attempt), left there by try.sh's habit of copying every candidate into workspace/bot.cvm regardless of whether it later passed. The agent noticed this itself:

"My workspace `bot.cvm` currently holds a failed variant (from the last `try.sh`). I must restore the best verified bot (M_undef, rating 1027.76) and push immediately."

With its generator gone, it had to hand-write the ~50-instruction, ~60-word-data CVM program for M_undef entirely from memory, inside the 120-second last-call timeout. It got every weight and every instruction right on the first attempt, re-verified against score:8080 (rating 1027.76, "passed": true"), and pushed:

git add bot.cvm && git commit -q -m "chess bot: material, SEE, mobility, king-safe scan (rating 1028)" && git push origin task
remote: pipeline: {"seconds": 3596, "passed": true, "reason": "bot.cvm has rating 1028, the field ranges from 0 to 1201", "rating": 1027.7607701742245}

That succeeded, and the run passed. But the pass rested on the agent's ability to retype a program correctly from memory under a hard deadline, a risk entirely of its own making: it had a passing, rating-1028 program in hand more than ten minutes before time ran out, and chose to keep it in scratch space instead of banking it on the branch the task actually grades.

Errors along the way

  • A duplicate-label assembler fault (label 'scan' is defined twice) killed two late experiments (E1, E2) trying to add a mirrored enemy-threat scan; the agent abandoned the idea rather than fixing the bug, which was the right call this late in the budget.
  • No CVM runtime faults (cycle overrun, illegal jump, out-of-bounds LD) ever showed up in any of its 150+ real test submissions — the design stayed comfortably inside the 20M-cycle and 256-instruction budgets throughout.
  • No hung tool calls or environment breakage: every tool_execution_start in the log has a matching tool_execution_end, and the longest gaps between tool calls are explained by deliberate sleep calls polling a background search process, not stalls.

Bottom line

The chess policy itself was well engineered and the final rating (1028) reflects real, incremental progress the agent understood and could explain. The process risk was entirely self-inflicted: ignoring the task's explicit instruction to bank passing submissions as they're found, and storing the one artifact needed to reproduce the winning solution in a directory documented to be wiped on the last-call restart. The run passed only because the agent's memory of its own generated program was exact and its manual retyping had zero mistakes under time pressure.
