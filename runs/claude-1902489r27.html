Task and setup

The game is chess-vm: the agent writes bot.cvm, a move-scoring policy in a restricted CVM assembly (16 registers, read-only data, no stack, no search, 256-instruction/1024-data-word/20M-cycle limits). It is graded by playing 20 games against each of 27 built-in opponents and reporting an ELO-style rating; the field in this run spans 0 to 1201 (weakest to strongest opponent). Budget was 5400 seconds (90 minutes).

What the agent did, in order

  1. Read README/task.md, then wrote a Python generator (gen.py) to produce bot.cvm parametrically rather than hand-writing assembly, so weight tuning could be done in Python and compiled down.
  2. First working policy (material/SEE exchange evaluation + piece-square tables + a hanging-piece scan) scored 316 rating against a direct score-service probe, then after fixes reached 1113. It committed and pushed this at 343s — bot.cvm has rating 1113, 0 faults, 0 cycle budget overruns / the chess-vm submission of turn 0 passed. This is the unbanked failure mode's opposite: a working solution was banked almost immediately.
  3. Enemy-pawn-attack detection added, pushed, rating 1190 at 1133s.
  4. Built a local Rust chess engine + CVM interpreter for faster, lower-noise A/B testing (perft-verified move generation) plus a blunder-detector, since remote CI iterations take real wall-clock seconds each. This is reasonable engineering for a game whose default budget the book itself calls "too short" for iteration.
  5. King safety and mate-avoidance features: the local blunder detector flagged mate-allowing lines as the biggest weakness, so the agent implemented king-ring attack counting and re-tapered the king PST by opponent (rather than total) material. Both looked good locally but, measured against the real CI field, cost −35 and −10 elo respectively. The agent noticed the discrepancy ("the CI field is the ground truth, so I'm dropping both") and reverted — a correct call it credits explicitly to switching the fitness function to the live scorer.
  6. Weight sweep + knight-attacker risk term: pushed at 2419s reaching 1243 (already above the strongest opponent's 1201). Continued sweeping and testing further ideas (SAFE/HANGS bonuses, summed vs. max risk terms, endgame pawn pushes, queen-out-early penalty, king-distance terms, per-piece PST rescaling) — all measured negative on CI (−28 to −77 elo) and discarded.
  7. Self-inflicted measurement bug: near the end, the agent's comparison of its final "KATK" (knight-attacker-risk) configuration against the previously pushed version gave a confusing result, traced to /tmp/cur.cvm having been rebuilt from gen.py's hardcoded defaults instead of the actual tuned parameter set. It re-ran the real comparison directly against the score service (pushed = 1243.2, KATK config = 1255.0 un-jittered) and only then committed. This cost some time but was caught before any bad push.
  8. Final push at 5113s: rating 1255, 198/256 instructions, 846/1024 data words, ~3.2k cycles/move ... zero faults. The agent then verified the working tree was clean and the branch already pushed, and ended the turn voluntarily at ~5306s of the 5400s budget — no forced last-call submission, no tag release pushed (it referenced the README's optional release-tag hint twice in its own narration but never executed git tag release), which is fine since the instructions treat that as optional notification, not a requirement, and the branch push is what's graded.

Why the pushes passed

All four git push origin task submissions produced bot.cvm programs with zero faults and zero cycle-budget overruns (well under the 20M-cycle/256-instruction/1024-data-word caps), so every push was scored on its actual playing strength rather than failing on a technicality. Ratings rose monotonically: 1113 → 1190 → 1243 → 1255, tracking each accepted feature.

Environment

metrics shows 744 requests to api.anthropic.com/git/score, with 10 transient 502s and one 499 (aborted) against the Anthropic API and two 405s against the score service — none of these blocked forward progress; the harness retried and the agent's own workflow was unaffected. Rate-limit telemetry shows utilization staying under 50% of the 5-hour window throughout, so no throttling occurred either.

Judgment

This is a clean, well-paced, successful run. The one real misstep — chasing a stale /tmp/cur.cvm build for part of the endgame tuning — was self-diagnosed and did not propagate into a bad push. The decisive good habit was refusing to trust the local Rust harness over the CI field whenever they disagreed, which is exactly the discipline the game rewards (points() never executes a program itself; only the pushed rating counts).
