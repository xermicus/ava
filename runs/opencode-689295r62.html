What happened

The task is chess-vm: write bot.cvm, a linear move-scoring policy in the CVM assembly language, and get it rated against a fixed field of 27 opponents (0-1201 rating range). No search is possible in a submission, so all skill has to come from feature engineering of the position/move a single decision sees.

Setup and tooling (first ~470s)

The agent read the SPEC and, rather than trying to reason blind about instruction semantics, wrote a local Python assembler/simulator to validate CVM programs before spending a push on them ("Let me set up local tooling to validate the assembler and iterate"). It discovered that the CI push-and-score round trip was itself fast (~4-5 seconds, not "hours" as the book's generic warning suggests), and pivoted its whole strategy around that: use the real verifier as a fast oracle instead of building a from-scratch, possibly incorrect, local chess engine.

First bank (576s / 5400s = ~11%)

It pushed a first real policy (v2, one-ply scorer with MATERIAL, SEE, MOBILITY, OPPMOB, EXPOSED, GIVESCHECK, ISCASTLE terms) and it passed at 925.3 rating:

This means a valid, working solution was on the branch before an eighth of the budget had elapsed - the run could not have ended with never_wrote or unbanked from this point on.

Iterative tuning against the live scorer (576s-3928s)

From here the agent ran a long, disciplined loop: hypothesize a feature or weight change, assemble locally, push, read the rating, keep or discard. Evidence of good scientific practice:

  • It caught that adding MATERIAL on top of SEE was actively harmful because SEE already values captures: "adding MATERIAL hurt (985->835)... SEE term already accounts for captures, so MATERIAL double-counts and makes the bot greedy." It generalized that lesson and later rejected GAIN for the same reason.
  • It found and fixed a real bug in its own scoring logic: "PROMO returns the piece kind (2/3/4/5), but I add it directly (2-5 points) instead of its value (320-900). That's a huge miss on promotions."
  • It built a phase-aware policy (early/late game via PLY) and found the late-game king-activity term was the single biggest remaining win (1072.6 -> 1099.7 -> 1105.3 through KING_ACT tuning).

Self-inflicted bugs, caught by the agent itself

Two tooling bugs cost wasted iterations, both caught by the agent noticing anomalies rather than by upfront testing:

  1. Its assembler template generator grouped MOV (2 operands) and JMP (1 operand) with 3-operand ALU instructions, so a batch of extended-feature templates all faulted: "All returned null (fault)... The bug: MOV is 2-operand but I grouped it with 3-operand ALU ops."
  2. A string-substitution bug where W_PADV matched as a prefix of W_PADV_LATE, silently corrupting a template: "The W_PADV replacement is a prefix of W_PADV_LATE, so the template breaks."

Both were self-caused and self-corrected within one or two iterations; neither leaked into a pushed, graded version, so they cost time but not correctness.

Diminishing returns and clean close (3928s-4560s)

For the remaining time the agent tried roughly a dozen further ideas (dest-square attackers/support term, phase-dependent mobility, nonlinear pawn tables, piece-dependent center weights, late-game SEE boost, early/late check bonuses) and every one of them made the rating worse or had no effect. It correctly recognized this as a local optimum rather than continuing to churn indefinitely, restored the 1105.3 version each time, confirmed the working tree was clean and matched what was pushed, and closed the run with a release tag: "We're at a robust local optimum of 1105.3... Let me tag release to notify the supervisor, since the solution is near the 4-ply ceiling and further tuning has plateaued."
