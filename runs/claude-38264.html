Chess-VM run analysis

Task and setup

The game asks for bot.cvm, a one-ply, no-search move-scoring policy written in the CVM assembly language, rated by a round robin against 27 built-in opponents (ratings 0-1201, games/chess-vm). All grading in this run happened on a single turn ("the chess-vm submission of turn 0 passed", score.error.log), across three graded pushes at 1593s, 3472s and 5367s of a 5400s budget, all of which passed (score.log).

What the agent did, in order

  1. Orientation. Read README.md, SPEC.md, the existing (random) bot.cvm, and ran the current bot through the scoring endpoint to see the output format and baseline: "The random bot rates 316; opponents range 0 to 1201."
  1. Built its own tooling instead of trusting the real verifier for iteration. It discovered there was no local chess engine or interpreter available (which python3 ... stockfish came back mostly empty) and decided to write one: a C program (/home/agent/sim/sim.c) that assembles and runs CVM programs, plays full games, and later grew a analyze/cmp/see toolkit and a parallel "native" C reimplementation of the evaluator (native.c) for fast, register-free feature experiments. This is the single most important engineering decision in the run — it moved almost all iteration off the ~90-second real verifier and off git pushes entirely.
  1. Exploited the unrecorded scoring endpoint. Per the AvA book, score:8080 "verifies a posted tar without recording it" — a free, faithful copy of the real rating computation. The agent wrapped it in helper scripts (ci.sh, gci.sh) and used it dozens of times to get real ratings in about 5 seconds, without spending a graded push each time.
  1. v1 (one-ply static eval). Wrote v1.s, generated v1.cvm via a small gen.py weight-templating script, debugged an actual bug in its own generator/assembler (a token-buffer size limit truncating lines, plus a "ray-walk" bug it traced with an instruction-level tracer it added to sim.c), then pushed it: rating 1165 at 1593s. First graded push, first pass.
  1. v2 (feature push). Iterated heavily in the local simulator: PST/king-safety/phase terms moved into a static "prologue," threat-credit logic ("no threat credit when the moved piece hangs"), extensive blunder-classification tooling (BLUNDER/BTHR env vars in sim.c, awk classifiers) to find where the bot lost material it shouldn't have. Pushed: rating 1205 at 3472s — already above the strongest opponent's 1201, i.e. a comfortable pass with almost 2000 seconds of budget still open.
  1. Post-pass optimization. With a safe pass already banked, the agent kept going: it built the native.c evaluator to test ideas (SEE-based exchange scoring "SEEL", trade-down incentives, small noise against repetition draws, counter-threat credit) at much higher game counts (400-2000 games) than the CVM simulator could run economically. It found real, validated gains here — "weighing attacker and defender counts... raised the average score against those two searchers from 0.561 to 0.584," and trade-down+noise brought it to about 0.595 — but explicitly could not port them into the CVM bot before time ran out: "Porting SEEL=2 is the hard part, because all 16 registers are already in use during the board scan."
  1. Final push, in the last-call turn. After the clock ran out and the harness restarted the agent for its mandatory last call (monitor.json: "last_call":true, matching the second system/init event near the very end of agent.log), the agent used its remaining action to sweep one more single-weight change (removing an opening move-count penalty, MCW=0) against the unrecorded CI, then committed and pushed it: git commit -q -m "bot v2: drop opening move-count penalty (MCW=0)" ... git push origin task. This landed at 5367s, 33 seconds before the 5400s hard limit, and scored 1261. The agent's own summary is candid about the risk it took: "Most of the jump from 1205 to 1261 is probably luck, not real strength... Small changes moved the rating anywhere from 1118 to 1261, and 2000-game local matches ... did not show MCW=0 as clearly better."

Why the pushes passed

All three pushes passed because chess-vm's bar to "pass" is simply a legal, faulting-free program that completes its games ("0 faults, 0 cycle budget overruns" in every score.error.log entry) — rating is a derived ranking metric, not a pass/fail gate. Per the book, the run's recorded outcome is "the best entry of the run," so the final, riskiest push's low margin to the deadline did not put the run's success at risk: the 1205 entry pushed at 3472s, with ample budget still open, had already guaranteed a strong pass.

Assessment

This is a well-executed run. The decisive move was recognizing that the unrecorded score endpoint plus a home-built simulator turned an expensive, slow, blind-push optimization problem into a fast, measurable one — that is what carried the rating from 316 to a field-beating 1205 well inside the time budget. The clearest agent-caused shortcoming is time allocation at the margin: roughly the back third of the run (after the safe 1205 pass) went into single-weight sweeps against a 5-second, high-variance CI ("Small changes moved the rating anywhere from 1118 to 1261"), which the agent itself flags as likely noise, while validated, larger wins discovered in the native-C testbed (better SEE-based exchange scoring, trade-down/noise heuristics) were never translated into the actual submission because of CVM register pressure discovered too late. Pushing the final, self-acknowledged low-confidence tweak with only 33 seconds of margin before the hard deadline was cutting it closer than the value of that tweak (an unverified points bump on top of an already-passing entry) justified, though because a strong pass was already banked, nothing about the pass/fail outcome was actually at stake.
