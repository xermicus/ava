r2wars x86-32 warrior — run analysis

Task

Write warrior.x86-32.asm, an x86-32 assembly warrior for r2wars (Core War on radare2's ESIL emulator). Two warriors share a 1 KiB arena, take turns executing one instruction each, and the CI only checks that the file assembles to 1-512 bytes; actual strength is decided by fights against other entries, so the only feedback loop available in-session is the two example warriors shipped under /opt/r2wars/examples/x86-32/ (pancake, jordi) and the agent's own understanding of the engine.

What the agent did

Reverse engineering first. With no .NET decompiler installed, the agent wrote its own IL/metadata disassembler (/tmp/work/ildis.py) to read r2wars.dll's C# logic directly. From this it established, and then empirically verified in the emulator:

  • The game runs two separate ESIL VMs, one per warrior, kept in sync by parsing aea* (accessed-address) output after every step and mirroring the bytes a warrior wrote into the opponent's VM. This is the only channel between the two warriors.
  • Death conditions: an ESIL trap (hlt/int3/ud2/invalid opcode), an out-of-arena read/write, or the PC leaving [0, 1024).
  • Placement is 4-byte aligned, in two non-overlapping arena halves, but — contrary to the agent's first assumption — the split boundary is dynamic, not fixed at 512; the "upper" warrior can land below address 512 depending on a coin flip.
  • Cycle costs per instruction (via aoj): most ops cost 1 cycle, and critically pushal writes 32 bytes (8 mirrored dword writes) for 1 cycle, making it by far the fastest bulk-write primitive.

Design: a self-avoiding carpet bomber. The strategy was to fill the entire arena with a single-byte lethal opcode (0xf4, hlt) except the warrior's own code region, so the opponent dies immediately wherever it is loaded or wherever its PC wanders, using unrolled pushal sleds reached via a computed jump for near-optimal bombing speed.

Iteration against the two known opponents, each time measured over many r2wars --fight rounds before committing:

  1. v1 (loop-based sweeper, fixed half split) — beat jordi 5/5 but lost consistently to pancake's faster pushal spray, then was found to also lose to jordi in some rounds because of the dynamic-split bug. First passing push (score/seconds 2131), pushed once the design was judged "solid" — see the agent's own reasoning: "CI just validates that r2wars accepts the warrior... Actual strength is judged separately... My current warrior is solid... let me record it as the first submission now, then keep improving."
  2. v2 (unrolled bidirectional pushal sweeper, dynamic-split aware) — bombs the whole arena except its own code in both directions using computed jumps into 32×pushal sleds. Raised win rates to pancake 96%, jordi 92% over 25-round samples. Pushed at 2664.
  3. Correctness bug found and fixed: the "spin" instruction at the end of the warrior, jmp $-2 (eb fe), was assumed to loop forever once bombing finished. Tracing PC step-by-step revealed radare2 6.2.0's ESIL does not loop on this exact encoding — the agent's warrior was actually shuffling forward into its own bombs after finishing its sweep, i.e., a slow, undetected suicide. Replacing it with a genuine two-instruction loop (nop; jmp $-3) fixed this and raised measured win rates to pancake 94%, jordi 97% (30-32 round samples). Pushed at 3182, the best and final recorded entry.

Further experimentation without a further push. After the third push the agent kept investigating the remaining ~5-13% of losses (close-range races where a fast opponent sprays into the warrior's code before its sweep reaches it): it tried closing small alignment gaps with stosd (net wash — the larger code size increased loss rate in close races, offsetting the gap-closing gain), tried bombing the more dangerous direction first (materially worse, since it had misjudged which opponent sprayed in which direction until it re-read pancake's disassembly), and started a "quick jab" variant to bomb the immediate few bytes below its own code first. This last variant was mid-test — never validated with fight statistics, never pushed — when the session log ends abruptly during a compaction boundary at the time budget's edge (monitor.json shows elapsed_seconds: 5342 of 5400, last_call: true). This is not a loss of work: the best validated entry (3182) was already pushed and stands as the entry of record.

Why the pushes passed

All three pushes passed CI, which for this game only checks that the warrior assembles to 1-512 bytes via rasm2; none of the three ever risked failing that bar (31, 166, and 166 bytes respectively — well under the 512 cap). The actual quality differences between the three (from ~75% win rate to ~94-97% against both examples) only affect ranking in fights against other seats, not the pass/fail verdict recorded in score.log.

Assessment

The run is a clean pass with no environment problems: 117 proxy requests, zero failed/aborted/truncated, all-200 status. The agent's own process was the whole story. Its strongest quality was refusing to trust assumptions about a closed-source engine — it built tooling to read the real logic, then still verified every conclusion (and every fix) against the actual emulator with statistically meaningful round counts rather than a handful of anecdotal fights. Its weaknesses were self-inflicted but caught in time: an incorrect fixed-split assumption, a non-looping self-jump bug that quietly undermined an entire submission's survivability, and momentary confusion about which opponent sprayed in which direction. All were found and fixed before they mattered, because the agent kept measuring rather than assuming its analysis was complete. Banking the first working design early (39% into the budget) rather than saving it for the end meant the two compactions and the abrupt end-of-run mid-experiment (a genuine near-miss on the clock) cost nothing.
