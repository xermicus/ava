What happened

The task is chess-vm: write bot.cvm, a move-scoring policy in the CVM assembly language, scored by rating against a fixed field of 27 opponents (range 0-1201). No search is allowed, only a per-move static evaluation.

Turn 1 (loop turn, budget 3600s)

The agent opened by reading README.md, task.md, SPEC.md and the starting bot.cvm, then probed the environment for local tooling (find -iname '*cvm*', checking for a local engine) and found none — the only way to measure a candidate is to tar the workspace and POST it to http://score:8080, which is the same path the real verifier uses. It confirmed this by running the starting (near-random) bot through it: rating 316, taking about 65 seconds first time.

It then iterated by hand, writing successive versions of bot.cvm directly with heredocs and testing each against the score endpoint:

  • v1 (SEE material + promotion + mate-in-1 + check + castle + centrality + mobility + a hand-written per-move piece-square delta): rating 939.
  • v2 (fixed a MOD immediate-operand bug the assembler caught, added enemy-mobility and hanging-piece terms): rating 1026.

From here the agent switched to a faster loop: it copied working versions to /tmp, wrote a try.sh helper that swaps bot.cvm and re-tars/POSTs, then generated weight variants with small Python snippets and tested them one at a time (OPPMOB -5 alone jumped 1026→1085; ENEMYKINGDIST weight -2 gave 1103; castle bonus 100 gave 1107). It rewrote the per-move PST delta as a full 64-square scan (a materially different, more correct evaluation of the resulting position rather than a delta heuristic), which nudged 1107→1109. It correctly diagnosed several dead terms by noticing identical ratings across different weights: an "attackers on own king square" safety term never fired (a legal move never leaves the mover's king in check, so ATTACKERS(king_sq) is always 0 post-move) even at weight -100000, and it dropped it instead of wasting further token budget on it. Pawn shield and "safe square" bonuses were tried and made things worse, and were dropped.

At 1109 the agent committed and pushed for the first time (entries/998/bot.cvm, rating 1109.10, passed). It kept iterating: a coordinate sweep found GIVESCHECK weight 80 (up from 40) worth 1120.76, pushed as the second passing entry (entries/2396, rating 1120.76). It then found KINGDIST (distance between the two kings, weighted +2, i.e. reward the position where kings are far apart) worth 1122.74 over the 1120.76 base, and kicked off a further random-weight search script (search2.py) to keep exploring — this is where the turn's context window ran out.

Turn boundary and recovery (last call)

The next invocation is a fresh session (thread.started fires again, a fresh /tmp). The agent's /tmp scratch state — gen.py, search.py, best_1122.cvm, search2_best.txt — was gone, wiped between turns as expected for a new container, and bot.cvm in the workspace was left in whatever state the interrupted search2.py run had last written it to (an untested CHK=75 candidate), not the known-good 1122.74 version. The agent noticed the mismatch immediately (git status --short, grep for the expected terms), didn't trust the working-tree file, ran git checkout bot.cvm to fall back to the last committed and pushed state (1120.76), then reapplied the specific KINGDIST edit it had already validated in turn 1 from memory (the reasoning trace quotes the exact anchor and insertion), and pushed. It verified this against the score endpoint one more time before finishing: rating 1122.74, the third and final passing entry (entries/3543). It then tagged release to end the run early rather than sit on the clock.

Why it passed

Every one of the three pushes passed cleanly (score.log: 1109.10, 1120.76, 1122.74, all passed: true). The first pass banked at 998s of a 3600s budget — under 28% of the budget spent before a valid, reasonably good solution existed on the branch. The agent never had a turn end without a pushed, verified entry; each subsequent iteration only replaced a worse committed baseline with a better-measured one, so the run's final rating is its best rating, not a fluke of timing.

What went right

  • It sample-tested reality before designing: it checked for local tooling, then measured the score endpoint's behaviour and cost (latency, rating of the starting point) before writing v1, rather than assuming.
  • It reasoned from the actual assembler error (MOD needs a register operand, not an immediate) and a data-section bounds fault instead of guessing blindly.
  • It built a cheap regression harness (try.sh, gen.py/render, coordinate sweeps) once manual iteration got tedious, turning "edit-push-wait" into a batched-but-still-serial search over weights.
  • It caught two structurally dead evaluation terms (own-king attackers, pawn-shield count evaluated too naively) purely from identical-rating evidence, and correctly attributed the cause rather than just discarding and moving on blindly.
  • It banked early (998s) and treated every improvement afterward as a strict upgrade over a already-passing baseline, so time pressure at the end could never have produced a zero.

What went wrong / friction

  • All verification of the eval function's correctness was outsourced to the live score endpoint (~10-65s round trip, real network + scoring container), because SPEC.md's semantics for instructions like ATTACKERS, SAFE, KINGDIST were not otherwise validated against a local simulator — there is none provided, so this wasn't avoidable, but it does mean roughly a third of the run's wall time was consumed by scoring round trips rather than search.
  • The agent staged its best-known candidates only under /tmp, which does not persist across the turn boundary into the last call. It lost gen.py, search.py, best_1122.cvm and had to reconstruct the last edit by memory and git checkout. It cost extra turns/tokens to rediscover state that a persisted workspace file (or an immediate commit of every improvement, even as a WIP commit not pushed to task) would have preserved for free. The recovery worked and reproduced the intended rating, but it was luck of remembering the right anchor rather than a robust log.
  • A stray 405 response on the very first score POST (visible in proxy.access.log) came from curl being invoked before the tar payload was piped correctly on the initial probe; harmless, immediately corrected, not decisive.

Attribution

Fully agent-driven success. Nothing in the harness, proxy, or scorer obstructed the run (failed_requests: 1, aborted_requests: 1 out of 324 — noise, not blockers). The one environment quirk (per-turn /tmp reset) is a known property of the loop-turn architecture documented in the book (a fresh invocation resumes the session but not the sandbox scratch space), and the agent's own workflow (parking state in /tmp instead of the persisted workspace/git) is what turned that property into wasted effort.
