What happened

The agent (deepseek-v4.1-flash, thinking high, on the chess-vm game) read README.md, task.md and SPEC.md, looked for a local engine or CVM interpreter to test against, and found none:

"No local engine — the CI is my only feedback loop. Let me build a baseline evaluation and test it."

It discovered that http://score:8080 accepts a posted tar and returns a verdict without recording it (per the book: "the score host on the same socket verifies a posted tar without recording it"), and used this as its private test harness via tar -c --exclude=.git . | curl ... http://score:8080.

First draft and the DIV bug

Its first bot.cvm combined mate-in-1, material, SEE, gain, check, castle, center, mobility and an "exposed king" term divided by a constant. Verified against the dry-run endpoint, score.error.log records:

bot.cvm has rating 316, 0 faults, 0 cycle budget overruns

Rating 316 is barely above the field's steady/positional-tier bots. The agent then edited the exposed-king term:

-    EXPOSED r10
-    DIV r10, r10, 8
-    SUB r0, r0, r10
+    EXPOSED r10
+    LDI r11, 8
+    DIV r10, r10, r11
+    SUB r0, r0, r10

CVM's DIV apparently needs a register operand, not a bare immediate literal 8 — this matches the fault seen elsewhere in score.error.log from a different, unrelated bad push ('8' is not a register, the registers are r0 through r15), confirming the instruction set is picky about immediates. Retesting through the dry-run endpoint after the fix:

bot.cvm has rating 944, 0 faults, 0 cycle budget overruns

The agent's own text: "Rating 944 (up from 316). Let me set up a quick submit helper and start tuning."

After the win: stall

No python-chess module was present, and rather than writing its own lightweight simulator or continuing to iterate weights through the dry-run endpoint it had already proven worked, the transcript shows only one more action: a git add -A && git commit -q -m "final submission" followed by git push origin task. Since nothing had changed since the prior commit, this was a no-op (proxy.access.log shows no second git-receive-pack), and productive tool use effectively ends here, about 8 minutes into a 3600+-second run.

From 15:34 on, proxy.error.log repeatedly logs:

and proxy.access.log shows POST /v1/messages calls to the model backend thinning out to one every several minutes, interleaved with 499 (client closed) and 404 responses on /api/hello probes, continuing all the way to 16:33. Why it passed

The pass was decided in the first eight minutes: the agent had a working, if unsophisticated, test loop (the unrecorded score endpoint), used it to catch a real bug, and pushed only after confirming a good result. That discipline — verify before banking — is what turned a mediocre 316 draft into a 944 push instead of a mediocre push.

Why it did not do better

Two things left points on the table. First, the agent's own follow-through was thin: once the quick python-chess check failed, it did not attempt any other path to keep tuning (e.g., a handwritten simulator, more targeted dry-run experiments on individual weights) and effectively downed tools. Second, from roughly the same moment the backend connection to llm.substrate.dev became unreliable (DNS failures, sparse successful calls, many stalled/aborted probes), so even had the agent wanted to keep iterating, the infrastructure gave it very few working turns to do it in, ending on a turn that never finished generating.
