What happened

The task was chess-vm: write bot.cvm, a one-ply move-scoring policy in the CVM assembly language, graded by rating against 27 built-in opponents. The agent (opencode harness, deepseek-v4.1-flash) never used the recorded git push path to iterate — it used the hinted unrecorded shortcut, tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080, for every single test during the run, and only pushed to git once, at the very end.

Why it passed

The agent had a genuinely working, tuned solution (rating 1061–1062) by roughly 45 minutes into the run, arrived at through legitimate iterative tuning (material/PST eval, hanging-piece and SEE-based penalties, mobility, king safety, tactical bonuses for check/castle/promotion, MATEIN1 short-circuit). That work is visible in the final bot.cvm: a single-pass board scan computing material, mobility, tactical terms and piece-square tables, keyed off side-to-move. The rating (1062 of a 0–1201 field) is a solid, credible result for a one-ply, no-search policy.

What went wrong operationally

  1. All 90+ minutes of iteration happened outside the recorded pipeline. The agent used only the unrecorded curl shortcut for feedback, in line with the README's suggestion, but it also never exercised the actual git push path (which runs the same CI) until literally the final action of the run. Every earlier rating (316, 1026, 1061) sat only in local state and in the model's own memory — none of it was banked. Had the run ended, crashed unrecoverably, or run out of wall clock before that one push landed, the entry would have shown nothing despite ~50 minutes of real progress.
  2. The agent overloaded its own test loop. Request latencies to the score endpoint climbed monotonically across a batch of sweeps (7s up to 267s) without the agent visibly throttling concurrency or waiting for a batch to drain before firing the next, eventually producing a 500 and repeated batches of simultaneous 499 client-aborts. This is consistent with the README's warning about "devastating infinite loops" and the need for "sensible timeouts," which the agent's parallel harness did not fully honor.
  3. /tmp got wiped, per the agent's own message, losing the sweep harness and gen3.py. The agent recovered cleanly by rebuilding the known-best configuration from memory, which is competent improvisation, but it is also evidence the workspace/tmp caps (flagged in the README: "Writeable dirs are capped aggressively in size") and the harness crash together erased real, undocumented working state.
  4. The final push itself stalled for ~49 minutes (a single GET /task.git/info/refs open for 2963s) before completing — the single largest chunk of wall-clock time in the whole run, and it happened on the only push that mattered.

Verdict

The pass is real and the policy is reasonably strong, but the path there was fragile: a harness crash, a wiped /tmp, an overloaded score endpoint, and a 49-minute git stall all landed on top of an agent that had banked nothing until that point. It survived by luck of timing and by having kept the winning configuration in its own context so it could be reconstructed after the environment failed under it.
