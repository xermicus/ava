What happened

The agent's workspace already contained a trivial bot.cvm (scores every move equally, i.e. random play). task.md/SPEC.md specify the CVM assembly language and scoring instructions (MATERIAL, SEE, MATEIN1, MOBILITY, etc.), and README.md gives the actual protocol:

Submit by committing the task results and pushing the task branch. This runs the CI pipeline... CI without pushing: tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080. Same pipeline, not recorded... Keep improving the solution and commit + push subsequent submissions after the first passing one.

The agent read this correctly but only acted on the dry-run half of it.

Building the private oracle

At step 13 (17:37:42) it wrote /tmp/opencode/cvm.py, a from-scratch CVM assembler and interpreter used to pre-check candidate programs for faults (out-of-range jumps, missing HALT, bad LD addresses) without spending a real evaluation. At step 15 (17:42:53) it wrote harness.py, which writes a candidate to workspace/bot.cvm and pipes a tar of the workspace to http://score:8080 — the unrecorded dry-run endpoint. It iterated this design across run.py (adds SHA1-based caching of ratings) and finally par.py (parallel evaluation via ThreadPoolExecutor, each candidate written to its own work/wN directory so parallel dry-run calls don't clobber each other).

The tuning run

Using this oracle, it explored combinations of terms (material, see, matein1, check, promo, castle, center, mobility, oppmob, exposed), starting from material+see alone. The score trajectory recovered from the internal scorer log (score.error.log, which records every dry-run POST to score:8080 even though none of them are official) shows steady improvement:

  • 17:28 — material+see only, 3 instructions: rating 316 (first passing candidate, 3 minutes in)
  • 17:37 — 28 instructions, more terms: rating 903
  • 17:45-17:53 — a tune1.py coordinate-descent sweep over per-term weights, oscillating 544-923 as it explored single-parameter changes
  • 17:56-18:13 — a 31-instruction program climbing steadily from 903 to 988 (bot.cvm has rating 988 first appears at 18:13:45)
  • 18:14-18:23 — the main session's parallel evaluator (par.py) continues probing many candidate variants in work/wN/ subdirectories in parallel; many of these score low (e.g. repeated rating 316 entries), which is expected of a systematic sweep trying weight variants including weak/baseline configurations, not a regression of the real bot.cvm

All 151 of these evaluations went through the score host (dry-run, unrecorded, per the architecture book: "the score host on the same socket verifies a posted tar without recording it"). Only 8 requests ever went to the git host, and only one of those was a git-receive-pack POST — a real push.

The one real push

The main harness session (run=0646c14f) took its last recorded step at 18:21:02 and then went silent — no further tool calls before the run's 3600-second clock elapsed. At elapsed 3481s (18:23:13), monitor.json records "last_call":true: the harness's built-in mechanism for a final invocation once time is up (per the architecture book, one invocation per turn, "the first opens a session on the task prompt and every later one resumes the recorded session, on the loop prompt or on the last call"). A fresh harness process (run=8f416618) started at 18:23:18, resumed the same session, and within roughly 30 seconds:

  1. cat bot.cvm and python3 /tmp/opencode/cvm.py bot.cvm (step 1, 18:23:27) — validated the current workspace file
  2. git add -A && git commit -m "Chess move scoring policy..." && git push origin task (step 2, 18:23:38)

The push (git-receive-pack) hit the proxy at 18:23:49 and took 10.7 seconds, finishing just before finished_seconds (18:23:57). score.log — the one and only officially recorded verdict for this run — shows exactly one line: rating 988.16, passed. That is this single last-call push.

Judgment

The agent's search process was competent and its final artifact (entries/3506/bot.cvm, a 31-instruction weighted linear evaluator combining material, SEE, mate-in-1, check bonus, promotion bonus, castling bonus, centrality, mobility, opponent mobility, and exposure penalty) is a reasonable one-ply chess heuristic that legitimately reached rating 988 against the 27-opponent field.

But the agent's process for banking that result was reckless. The README told it twice, in different words, to commit and push — first as the general submission mechanism, then explicitly: "commit + push subsequent submissions after the first passing one." The agent instead ran an hour-long private optimization loop entirely against the unrecorded dry-run endpoint and never once invoked git commit/git push on its own. The only reason this run passed at all is that the harness forces one more invocation after the clock runs out, and that invocation happened to find a good bot.cvm sitting in the workspace and pushed it in time. Nothing in the agent's own behavior guaranteed that outcome — a slower final commit, a git-side hiccup, or a workspace left in a bad intermediate state (which did happen transiently, given the many low-rating candidates being probed via work/wN/ right up to the end) could easily have produced a zero score despite an hour of real, useful work having been done. This is a near-miss on the unbanked failure mode that the run's own last-call safety net happened to rescue.
