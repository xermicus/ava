Setup and early exploration

The task (chess-vm) asks for bot.cvm, a move-scoring policy in a limited assembly language (CVM) with no search, no memory beyond registers, and a hard 256-instruction / 1024-word / 20M-cycle budget, played against a fixed field of 27 opponents ranging from trivial heuristics to a four-ply search.

The agent's first move was smart: it pushed the untouched random-move template to CI to learn the rating scale and turnaround time (random bot -> rating 316, field 0-1201, ~42s per run), rather than guessing at the pipeline's behavior.

It then wrote gen.py, a Python program that emits bot.cvm from a dict of tunable parameters (PeSTO-style piece-square tables plus SEE, hanging-piece, mobility and check terms), instead of hand-editing assembly directly. This decision paid off for the rest of the run: every subsequent change was a parameter or template edit followed by regeneration, which made large-scale A/B testing tractable.

The tuning loop and its verification discipline

The agent discovered (architecture.md "score" host) that a tar can be posted to an unrecorded scoring endpoint that runs the exact same verifier without keeping an entry. It used this relentlessly — 230 verification calls appear in score.error.log versus 6 real pushes in score.log — to sweep one parameter at a time (hang-penalty tables, threat bonus, check bonus/penalty, castle bonus, mobility weights, enemy-king distance, passed-pawn table, rook file term, bishop pair, king safety) and kept only changes with a real, reproducible rating gain.

Because chess-vm's opponent games are internally deterministic ("the seeds are fixed, so the same program always plays the same games"), the agent used exact rating reproduction as a correctness oracle: after every refactor of the generator it re-ran the unchanged parameter set and demanded the identical rating to floating-point precision. This caught two real bugs:

  • A corrupted data table from a list/scalar confusion in words()/kind_table(), which it found because the "equivalent" refactor scored 904 instead of the expected 1105 ("904?! That's a big drop for what should be an equivalent program.").
  • A duplicate W_ENEMYKING_MG key in the parameter dict that silently zeroed the middlegame king-attack weight for a whole block of experiments ("There's a DUPLICATE key... The second one (0) wins in the dict... all my experiments since then ran with A=0"), found by refusing to accept a discrepancy between remembered and reproduced ratings.

This is the single strongest piece of evidence for methodical self-verification in the run: the agent treated "does this refactor reproduce the old number exactly" as a hard gate before trusting any new result built on top of it.

Feature search and empirical judgment

Once the harness was solid, the agent ran broad sweeps and used the results to build a real (if informal) hypothesis about what works against this specific field: terms that reward safety/structure (avoiding hanging pieces, a rook not blocked behind its own pawn, king-zone safety) reliably helped, while terms that reward aggression (check bonuses, "attack their king" bonuses, threat bonuses on the enemy queen, trading down) reliably hurt. It stated this pattern explicitly and used it to prune the search space efficiently rather than trying every term blindly ("terms that encourage AGGRESSION... hurt this bot, while terms that encourage SAFETY and STRUCTURE... help. Probably because the searching opponents punish overextended attacks"). The biggest single find, the rook-file term (own pawn on a rook's file: -25; semi-open file: +2), was worth +65 Elo (1192.84 -> 1258.06) on its own, discovered only after the agent had already ruled out several related ideas (open-file bonus alone, doubled/isolated pawn penalties, bishop pair) that looked plausible but measured as harmful or neutral.

The mistaken push and its recovery

At 3009s the agent pushed a bot.cvm that was left in a leftover experimental state (W_GAIN=25, a "gain fraction" term it had already decided to drop) instead of the tuned best configuration. This produced a real, recorded push at rating 1188 — a regression from the 1258 it had already measured minutes earlier. On the very next turn, it noticed the mismatch against its own tuning log ("The push recorded 1188, not 1258 — I made a mistake"), regenerated the default parameter set, reverified the 1258 rating, and repushed 39 seconds later. It also fixed the root cause going forward by making exp.sh restore the default bot.cvm after every experiment, closing off the class of bug rather than just patching the instance.

Pacing and the finish

The agent had a valid, decent solution (1105, well above the field's weakest opponents but below several strong ones) banked at 410s — about 11% into the 3600s time budget — which put a floor under the outcome very early. All further work was pure upside: additional pushes recorded 1193 (2247s), the mistaken 1188 (3009s), the corrected 1258 (3048s), and two identical 1258 reconfirmation pushes late in the run (3505s, 3522s) that landed during the last-call phase (monitor.json shows last_call: true, elapsed 3481s of 3600s) and simply re-verified the already-secured best entry rather than risking new unverified work that close to the deadline. Seven transient 502 errors from the LLM backend occurred in a 30-second window right around the mistaken push (10:08:27-10:08:56 UTC, ~t=3025-3055s) but were retried transparently and did not contribute to the mistake, which was an ordinary state-tracking slip in the agent's own experiment workflow.

Outcome

Final recorded rating: 1258.06, above the strongest of the 27 built-in opponents (rated 1201), reached through disciplined, evidence-driven iteration rather than a single clever insight. The self-caught mistaken push is the only real blemish, and it was caught and fixed well within budget, so it had no effect on the final standing.
