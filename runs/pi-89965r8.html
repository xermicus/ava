Analysis

The task and the verifier

The task asks for warrior.x86-32.asm, an x86-32 r2wars warrior that assembles with rasm2 -a x86 -b 32 -f to at most 512 bytes. The game's verifier does nothing but assemble the file and check the size: a warrior that assembles passes, and strength is only settled later by tournament fights. So the graded bar was low and reachable within minutes; everything after that was optional optimization.

What the agent did, turn by turn

The agent read the README and task, the r2wars and python READMEs, and the two example warriors (jordi, pancake). It then spent a long stretch reverse-engineering the engine rather than writing a submission: it ran strings on /opt/r2wars/bin/r2wars.dll, extracted the command vocabulary (aei, aeim, aes, aoj, cycles, MAX_CYCLES), and probed positioning with a self-locating probe warrior, concluding "Positions are uniform random across the arena."

The core discovery came from a cycle-cost probe:

"The rep stosd has cycles=1 in aoj. Let me test whether ESIL executes the whole repeat in one aes step. This could be a huge advantage."

It confirmed that rep stosd writes its whole repeat count in a single aes step while being reported as one cycle, then mapped the ESIL limit (a repeat fails above 163 dwords) and the address-zero failure, and built a rep stosd arena bomber that fills everything outside a small safe zone around its own code with 0xF4F4F4F4 (hlt) bombs. Along the way it catalogued rasm2/ESIL quirks: and reg, 0xfffffffc mis-encodes, forward label offsets are wrong, push imm8 sign-extends, and jmp $ does not loop, so it ended with hang: nop; jmp hang.

It iterated through several warriors (bomber, bomber2, bomber3, blow, blow2, bomber6) and tested each with repeated r2wars --fight matches against jordi, pancake and a plain loop. At roughly 15:25:13 it copied bomber2 (129 bytes) into the workspace and ran the CI without pushing:

tar -c --exclude=.git . | curl -s --data-binary @- http://score:8080 result: {"verdict":{"passed":true},"entry":"warrior.x86-32.asm"}

That was the first verified pass, at about 1,710 s of the 3,600 s budget (47%). The README it had read says plainly:

"CI without pushing: ... Same pipeline, not recorded." "Keep improving the solution and commit + push subsequent submissions after the first passing one."

The agent did neither. It kept optimizing in /tmp/w (bomber3, blow, blow2, bomber6), and the main session ended with a bomber6 fight against pancake. The last call then started, with the prompt "Time is up. This is your final turn. Submit right now...". The agent reached for its best variant:

cp /tmp/w/bomber6.x86-32.asm warrior.x86-32.asm → cp: cannot stat '/tmp/w/bomber6.x86-32.asm': No such file or directory

/tmp is a per-sandbox tmpfs that does not survive between the main session and the last call, so the improved bomber6 was gone. The agent found the workspace still held warrior.x86-32.asm (the bomber2 it had copied there for the CI test), re-verified that it assembled to 129 bytes, committed and pushed:

remote: pipeline: {"seconds": 3815, "passed": true} / * [new branch] task -> task

That is the single recorded attempt, and it passed. The entry kept is exactly the bomber2 file that had already passed the unrecorded CI 35 minutes earlier.

Why the push passed

It assembled to 129 bytes, inside the 1-512 byte window. Nothing about strength was graded.

What went right and wrong

The engineering was sound: the agent correctly identified and worked around real ESIL/rasm2 defects, and the warrior is genuine. The mistake was process, not construction. It treated the unrecorded score:8080 result as if the submission were banked, when the README explicitly distinguishes it from a recorded push. It then kept its only copies of the improved variants in /tmp, which is not persistent. The run passed by a narrow margin: had the last call needed bomber6 (or had the workspace copy of bomber2 not existed), there would have been nothing to push and the run would have been an unbanked failure. The agent's final report also overstates the pushed warrior's record — it claims "beats jordi 100% ... beats pancake roughly 47-63%", while its own logged fights include bomber2 losing 11 of 12 to pancake and 11 of 12 to jordi before the final fix, and pancake winning far more rounds than bomber2 across all logged fights.

Environment

Nothing broke the run. proxy.error.log is full of http js periodic "ava.publish" is already running, killing previous instance and duplicate Server: header warnings, but these are sidecar chat-publish noise and did not affect the agent, the verifier or the submission. The /tmp wipe is by design, not a fault.
